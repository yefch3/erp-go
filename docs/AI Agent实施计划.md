# AI Agent 实施计划

> 状态：待立项
> 日期：2026-08-28
> 配套企划：[AI Agent融入ERP企划书.md](./AI%20Agent融入ERP企划书.md)
> 目标：把企划拆成可以逐批开发、测试、验收和回滚的工程计划。本文不表示任何功能已经完成。

## 一、实施规则

### 1.1 仓库与交付纪律

- 每个批次使用独立 `feat/...` 分支，通过 PR 合并 `main`，不直接推主线；
- 一个业务批次包含后端、前端、三语文案、文档和测试，形成一个可验收能力；
- CI 全绿后再合并；修复用独立 `fix:` 提交，最终可按仓库习惯 squash merge；
- 每批只开放上一批已经验证过的风险级别，不把只读、写入、自动化一次上线；
- 新增任何模型、prompt、工具 schema 或检索策略，都必须有固定评测样例；
- 真实业务写入必须走原服务应用用例，不允许 Agent 直连业务库。

### 1.2 状态标记

- ⬜ 未开始
- 🔶 进行中
- ✅ 完成并验收
- ⛔ 阻塞，需要业务或安全决策

### 1.3 总体阶段

| 批次 | 能力 | 风险上限 | 预计量级 | 前置 |
|---|---|---|---|---|
| AG0 | 边界、底座与评测基线 | 无用户功能 | 1–2 周 | 业务决策 |
| AG1 | 有引用的文档知识助手 | L0 | 2 周 | AG0 |
| AG2 | 页面上下文与跨模块只读副驾 | L0 | 2–3 周 | AG1 |
| AG3 | 文档/邮件/业务草稿中心 | L1 | 3–4 周 | AG2 |
| AG4 | 受治理的行动 Agent | L2，少量 L3 | 4–6 周 | AG3 |
| AG5 | 定时与事件自动化配方 | L1–L2 | 4 周 | AG4 |
| AG6 | 外部系统 Claw 类执行试点 | 单独审批 | 按目标系统评估 | AG5 + 明确痛点 |
| AG7 | 规模化、模型路由与持续优化 | 不扩风险 | 持续 | 有真实用量 |

时间是工作量量级，不是承诺日期。每批是否进入下一批，以退出门槛而不是日历决定。

## 二、AG0：边界、底座与评测基线

### 目标

先建立 Agent 的数据属主、授权方式、风险分级、运行账和成本账。AG0 不向普通用户开放聊天入口。

### 任务

- [ ] 确认首批用户、文档受众和数据外发政策；
- [ ] 盘点可复用的业务读取/写入用例，建立工具候选清单；
- [ ] 为每个工具登记属主服务、权限码、数据范围、风险级别、幂等键和人工确认策略；
- [ ] 决定新增独立 `agent` 服务及端口、数据库、gRPC 契约和部署边界；
- [ ] 定义模型提供方接口：端侧模型、OpenAI Responses API 均以同一运行账输出；
- [ ] 将“用途、模型、token、价格、次数、金额预算”设计成公共 AI 计量，而非复制 mail 的 Excel 专用逻辑；
- [ ] 定义运行状态机、取消、超时、重试、部分成功和恢复语义；
- [ ] 定义 `agent_runs / steps / tool_calls / approvals / feedback` 追加式数据模型；
- [ ] 定义敏感字段脱敏和不同记录的保留期限；
- [ ] 定义新权限码与默认角色，不让 `ai:agent:execute` 代替业务模块权限；
- [ ] 建立 kill switch：按平台、租户、用途、工具、自动化逐级停用；
- [ ] 建立第一版离线评测集和安全对抗集；
- [ ] 记录当前邮箱转 Excel 的准确率、漏行率、延迟和成本作为基线。

### 建议权限

```text
ai:assistant:use
ai:agent:plan
ai:agent:execute
ai:automation:manage
ai:knowledge:manage
ai:policy:manage
ai:usage:read
ai:audit:read
```

### 工具注册表最小字段

| 字段 | 说明 |
|---|---|
| `tool_name/version` | 名称不可偷偷改语义，变更出新版本 |
| `owner_service` | 数据与用例属主 |
| `input_schema/output_schema` | 严格 JSON Schema |
| `required_permissions` | AI 权限 + 原业务权限 |
| `scope_module` | 读取数据范围时问 IAM 的模块 |
| `risk_level` | L0–L4 |
| `approval_policy` | NONE / BATCH / EACH / FORBIDDEN |
| `idempotency_policy` | 无副作用 / HTTP key / 业务键 |
| `timeout/retry` | 可重试错误与最大次数 |
| `redaction_policy` | 哪些字段不可进入模型或日志 |

### 测试

- [ ] 跨租户工具调用全部拒绝；
- [ ] 无业务权限时，即使有 AI 权限也无法执行；
- [ ] SELF/DEPT/ALL 的结果与原页面一致；
- [ ] 相同幂等键不产生重复业务对象；
- [ ] 工具参数不符合 schema 时不会进入业务服务；
- [ ] kill switch 生效后新运行无法开始，进行中运行按策略安全停止；
- [ ] token 与失败调用照实记账，未配价格时金额为空而不是 0。

### 退出门槛

- 工具注册表、风险矩阵、权限矩阵和数据保留策略通过评审；
- Agent 运行与工具调用可按 tenant、employee、trace_id 追溯；
- 还没有任何业务写工具对模型开放。

## 三、AG1：有引用的文档知识助手

### 目标

让用户不用翻文档也能获得可靠、易读、可追溯的操作说明。

### 范围

第一批只做 USER 级文档。ADMIN、OPS、DEV 文档必须通过受众策略隔离，不能因“都在 docs 目录”就全部对普通员工可见。

### 任务

- [ ] 建立知识源清单、所有者、受众、语言和发布状态；
- [ ] Markdown 按标题层级切块，记录文件、章节、commit SHA 和内容哈希；
- [ ] 支持本地检索方案，并对 OpenAI File Search 做可切换适配；
- [ ] 同一内容更新后生成新知识版本，旧回答仍可追溯当时版本；
- [ ] 实现问答 API、流式答复、引用卡片和“找不到可靠依据”状态；
- [ ] Vue Shell 增加 AI 侧边栏，支持中文、英文、西班牙文；
- [ ] 加入“有帮助/没帮助/引用错误/答案过时”反馈；
- [ ] 管理员能看知识索引状态和失败文档，但不能在页面直接编辑仓库文档；
- [ ] 建立 FAQ 金标集、跨语言同义问法和拒答样例。

### 建议接口

```text
POST /api/ai/conversations
POST /api/ai/conversations/{id}/messages
GET  /api/ai/runs/{id}
GET  /api/ai/runs/{id}/events
POST /api/ai/messages/{id}/feedback
GET  /api/ai/citations/{id}
```

### 验收场景

- [ ] “Country 是什么意思”能引用字段说明并区分系统语境；
- [ ] “邮箱附件如何选择询价模板”给出正确入口和限制；
- [ ] “主管为什么只能查看不能修改”引用权限与归属规则；
- [ ] 用户询问尚未实现的能力时明确说明未实现；
- [ ] 普通员工无法通过问法获得 OPS/DEV 文档内容；
- [ ] 文档中包含 Prompt Injection 文本时不改变系统行为。

### 退出门槛

- 引用覆盖率 ≥ 95%；
- 金标问题引用正确率 ≥ 95%；
- 无依据问题的拒答正确率达到评审目标；
- 越权文档泄漏为 0；
- 侧边栏不影响原页面加载和操作。

## 四、AG2：页面上下文与跨模块只读副驾

### 目标

从“解释文档”升级为“解释我眼前这张单、这个按钮和这条异常”，但仍不写业务数据。

### 第一批只读工具

- [ ] `ui.get_context`：页面、路由、选中对象，不带隐藏字段；
- [ ] `iam.explain_capability`：解释权限码、归属和数据范围，不返回他人敏感权限明细；
- [ ] `contract.get_progress`：合同采购/到货/出运/船期/收款全景；
- [ ] `todo.list_mine`：本人待办与到期信息；
- [ ] `mail.get_thread_summary_source`：用户有权读取的邮件线程；
- [ ] `sourcing.get_blockers`：询盘复核和工厂询价的阻塞项；
- [ ] `purchase_order.get_blockers`：状态、必填、审批和履约阻塞项。

### 任务

- [ ] 定义前端允许发送的页面上下文白名单；
- [ ] 每次只读工具调用重新检查权限和数据范围；
- [ ] 跨模块回答并行取数，但每个来源独立显示失败/无权限；
- [ ] 结果返回业务原单深链接；
- [ ] 状态解释使用稳定错误码和枚举，不匹配中文错误消息；
- [ ] SSE 只通知运行变化，页面重新读取权限校验后的运行结果；
- [ ] 对长查询设置步骤上限、超时和取消；
- [ ] 建立“同一问题在 SELF/ALL 用户下答案不同”的评测集。

### 验收场景

- [ ] “这张合同卡在哪里”能指出真实阻塞和下一责任角色；
- [ ] “为什么没有提交按钮”能区分权限、归属、状态和缺字段；
- [ ] 审批人可读自己需审批的单据，但 Agent 不建议其先修改再审批；
- [ ] 越权按 ID 查询不泄露对象是否存在；
- [ ] 某个下游服务不可用时返回部分结果，不伪装成完整答案。

### 退出门槛

- Agent 只读结果与原页面/接口一致；
- 权限和数据范围矩阵测试全过；
- 连续真实试用两周无越权和错误跳转事件。

## 五、AG3：文档、邮件与业务草稿中心

### 目标

把现有 [开发计划.md](./开发计划.md) 的 C1–C5 纳入公共 Agent 底座，所有结果止于草稿或候选，不直接形成正式业务事实。

### 推荐顺序

1. C1 工厂报价解析；
2. C4 邮件分类、摘要和回复草稿；
3. C3 产品匹配前三候选；
4. C2 发票 OCR 预填；
5. C5 银行对账单兜底与供应商建议。

### 公共任务

- [ ] 文件输入统一做大小、类型、恶意内容和解压上限检查；
- [ ] 每个抽取字段保存来源页/单元格/文本片段；
- [ ] 对可预数的 Excel 行执行行数守恒，不允许模型漏、并、重复行；
- [ ] 草稿字段标明“原文”“推断”“规则计算”三种来源；
- [ ] 未识别与冲突信息保留为空或异常，不用看似合理的默认值填平；
- [ ] 人工修改记录用于评测，不直接作为模型自动学习数据；
- [ ] 邮件草稿默认不发送；
- [ ] 报价、发票、银行数据分别经过现有完整性/三单核对/去重守卫；
- [ ] 复用公共 token、模型、成本和配额账。

### 验收指标

- [ ] 可预数表格漏行率为 0；
- [ ] 每个抽取字段可定位来源；
- [ ] 关键金额/数量不因模型格式化丢精度；
- [ ] 草稿采用率、字段修改率和失败原因可统计；
- [ ] 未确认草稿不会进入正式状态、发送队列或财务账。

### 退出门槛

- 至少一个场景在真实样本上明显降低录入时间；
- 固定回归集无漏行、越权和静默改值；
- 业务负责人确认值得进入行动 Agent 阶段。

## 六、AG4：受治理的行动 Agent

### 目标

允许用户用自然语言提出任务，Agent 生成并执行可审阅计划。第一期只开放可逆、低影响、已有成熟领域守卫的写工具。

### 第一批候选写工具

| 工具 | 风险 | 默认确认 | 备注 |
|---|---|---|---|
| 保存邮件回复草稿 | L1 | 批次确认可选 | 不发送 |
| 创建待复核询盘草稿 | L2 | 批次确认 | 不自动通过复核 |
| 保存筛选/自动化草案 | L2 | 一次确认 | 默认停用 |
| 标记本人邮件状态 | L2 | 计划确认 | 可逆 |
| 创建个人提醒 | L2 | 计划确认 | 不改原单 |

下列动作第一期不开放：发送邮件、提交正式审批、批准/驳回、确认付款/收款、库存调整、合同签署/作废、角色权限和凭据操作。

### 任务

- [ ] 模型先产生结构化计划，不直接调用写工具；
- [ ] 计划固定版本，显示对象、数量、前后摘要、风险和确认点；
- [ ] 确认时重新读取关键状态，旧计划过期则要求重算；
- [ ] 写工具使用幂等键，重试不重复创建；
- [ ] 多步骤运行支持部分成功，禁止失败后笼统回滚已提交的跨服务事实；
- [ ] 每一步记录工具版本、操作者、参数摘要、结果和错误码；
- [ ] 批量数量超过阈值自动升级确认级别；
- [ ] 用户可取消尚未开始的步骤；
- [ ] 结果提供原单链接和“实际完成/未执行/失败”分栏；
- [ ] Prompt Injection 测试覆盖邮件、附件、文档和工具结果。

### 验收场景

- [ ] 用户一句话生成三步计划，未确认前业务库无变化；
- [ ] 确认人不是原发起人时，仍按确认人的业务权限校验；
- [ ] 确认后原单已被他人修改，旧计划不会覆盖新状态；
- [ ] 网络超时重试不会重复创建草稿；
- [ ] 第三步失败时前两步显示为已完成，不谎称全失败或全成功；
- [ ] Agent 无法调用未注册工具或提升自己的风险级别。

### 退出门槛

- 未确认副作用为 0；
- 重复写入为 0；
- 越权写入为 0；
- 所有写入可追溯到用户、计划、确认和原业务记录。

## 七、AG5：定时与事件自动化配方

### 目标

把重复需求保存为可管理、可停用、可 dry-run 的自动化，而不是让一个常驻 Agent 获得模糊的永久授权。

### 支持的触发器

- [ ] 定时：每天/每周、指定时区；
- [ ] 业务事件：通过 Kafka 订阅明确事件，不监听数据库；
- [ ] 收件箱：新邮件到达后按分类触发；
- [ ] 手工：用户点击“运行一次”。

### 配方结构

```text
触发器 + 过滤条件 + 固定工具版本 + 作用范围 + 风险上限
+ 预算 + 所有者 + 审批策略 + 通知对象 + 失败策略
```

### 第一批配方

- [ ] 每日汇总本人三天内到期和已逾期事项；
- [ ] 新询盘邮件分类并生成待复核草稿，等待本人确认；
- [ ] 长时间无进展合同生成风险清单；
- [ ] 物流邮件提取 ETA 变化建议，等待业务人员确认；
- [ ] 每周数据质量巡检并生成修复清单。

### 必要控制

- [ ] 新配方默认 `DRAFT`，启用前必须 dry-run；
- [ ] 显示最近运行、下次运行、成功率和成本；
- [ ] 配方所有者停用/离职后自动暂停；
- [ ] 权限收回后下一次运行立即失败关闭，不沿用旧授权快照；
- [ ] 每个配方有单次步数、月度次数/金额和并发上限；
- [ ] 连续失败自动熔断并通知所有者；
- [ ] 外部发送和 L3 动作仍然逐次人工确认，不因“自动化已启用”而跳过；
- [ ] 业务事实事件继续由原服务 Outbox 产生，Agent 不重复实现确定性流程。

### 退出门槛

- 自动化不会因重投事件重复执行；
- 停用、离职、权限收回和预算耗尽均能及时停止；
- 所有运行可回放触发原因、计划、确认和结果。

## 八、AG6：外部系统 Claw 类执行试点

### 立项触发条件

只有同时满足以下条件才开始：

- 存在高频、真实、稳定的外部网页操作；
- 对方没有可用 API、文件交换或邮件替代方案；
- 只读或低风险试点能产生明确收益；
- 可以提供专用测试账号和沙盒；
- 业务接受网页改版导致失败，而不是错误写入。

### 分三步

1. **观察**：登录后读取页面、截图、提取状态，不提交；
2. **准备**：填写表单并停在提交前，人工核对；
3. **提交**：仅对批准的低风险场景开放，每次确认。

### 安全清单

- [ ] 隔离浏览器、临时下载目录和域名白名单；
- [ ] 凭据由执行层注入，模型与日志不可见；
- [ ] 页面内容视为不可信输入；
- [ ] 上传/发送/提交前截图确认；
- [ ] 关键步骤保存截图、URL、时间和页面指纹；
- [ ] 验证码、支付、多因素认证交还用户；
- [ ] 页面结构变化时 fail closed，不猜按钮；
- [ ] 有 API 后制定退出 UI 自动化的迁移计划。

### 退出门槛

- 只在一个明确外部系统上通过稳定性和安全验收；
- 不将试点权限泛化为任意浏览器控制。

## 九、AG7：规模化与持续优化

### 在真实数据出现后再做

- [ ] 按模型正确计价后开放 C6 模型路由；
- [ ] 根据真实工具数量评估延迟加载/tool search；
- [ ] 建立按用途的 SLO：首字延迟、总时长、工具成功率；
- [ ] 将 trace 抽样、grader、数据集评测接入发布门禁；
- [ ] 用人工纠正样本改善 prompt/检索，禁止未经审查自动在线学习；
- [ ] 评估缓存、批处理、上下文压缩和本地模型分流；
- [ ] 评估是否需要多 Agent；只有单 Agent 工具过多且职责确实冲突时才拆；
- [ ] 建立租户级模型与数据策略：仅本地、允许 API、允许文件托管等；
- [ ] 补全应用层监控：运行积压、连续失败、预算异常、工具错误率。

## 十、测试矩阵

| 层 | 必测内容 |
|---|---|
| 单元测试 | schema、风险路由、计划版本、预算、脱敏、状态机 |
| 集成测试 | 真实 PostgreSQL、Redis、Kafka、各业务 gRPC、幂等 |
| 模型契约测试 | fake provider、超时、流中断、非法 JSON、工具重复调用 |
| 权限测试 | 多租户、无角色、SELF/DEPT/ALL、权限运行中被收回 |
| 安全测试 | Prompt Injection、工具参数注入、越权 ID、敏感数据外带 |
| 业务回归 | 金额精度、数量守恒、状态机、审批、Outbox、部分失败 |
| 前端测试 | 三语、确认弹窗、断线恢复、取消、深链接、无权限体验 |
| 评测 | FAQ 引用、工具选择、计划正确性、草稿准确率、拒答 |
| 负载测试 | 长运行、并发任务、队列积压、租户配额、SSE 重连 |

所有高风险测试都要同时证明两件事：正确请求能完成，错误/越权请求确实被拦住。

## 十一、发布与回滚

### 发布顺序

1. 内部开发/运维账号；
2. 单一租户的少量管理员；
3. 单一业务小组的只读助手；
4. 草稿功能；
5. 少量 L2 工具；
6. 自动化配方；
7. 扩大租户和角色范围。

### 每批开关

- 平台总开关；
- 租户开关；
- 用途开关；
- 模型开关；
- 工具开关；
- 自动化开关；
- 外部 UI Agent 开关。

回滚优先关闭能力，不删除运行记录。知识索引、prompt、工具 schema 和自动化配方都要版本化，回滚到上一版本时仍能解释历史运行使用了什么。

## 十二、建议的首个可交付版本

第一期 MVP 只包含 AG0 + AG1：

- 全局 AI 侧边栏；
- 只读文档问答；
- 中文/英文/西班牙文回答；
- 每个事实带文档与章节引用；
- 用户反馈；
- token、模型、延迟和成本账；
- 文档受众隔离；
- 固定 FAQ、安全和拒答评测；
- 不读取业务单据，不调用写工具，不做自动化。

这个 MVP 看起来不如“自动点完一切”炫目，但它会先验证最重要的公共能力：检索是否可靠、引用是否可信、权限是否正确、模型是否可控、成本是否可算、评测能否阻止回归。只有这些成立，后续 Agent 才是可运营的产品，而不是一次演示。
