# D1 具体修改与验收方案（仅方案，尚未实施）

依据：本目录正式需求原样快照，客户询盘全部、采购询价全部、物流询价全部；客户报价的数据接收/已提交源报价查看及同步清除部分；对应角色权限及真实来源待办。辅助清单D1、I01～I04、I17用于测试组织。与正式原文不一致时按正式原文核对，不用旧测试改写需求。

本方案不构成本轮实施记录。用户本轮仅授权D0，故不会继续编辑业务代码或数据库。

## 1. D1 完成后的可验收行为

销售在客户询盘保存、提交或撤回；提交后采购与物流直接看到有效需求，客户报价自动出现。采购按工厂为部分或全部产品保存/提交报价；物流按货代运输方案保存/提交多币种费用；保存未提交销售不可见，提交后销售能直接查看完整报价，部门有权限同事可修改已提交报价并同步。销售撤回清除当前轮双方报价和未确认客户报价，重提按新内容报价，旧打开页面不能写回旧报价。对应待办跳转原业务、继承权限。

本批不做五条公式、PDF、客户确认建立合同、合同确认签署、财务放行、实单最终重新询价/拆单、银行流水退役、出账、质检、正式船期提醒全链。为撤回保护现有已确认报价/已存在合同而必需的只读检查属于D1依赖，不借此重构合同流程。

## 3. 数据与并发技术设计约束

1. `submitted_at`或等价内部标记只服务保存/提交可见性，不给用户增加“草稿”状态。采购/物流询价状态由已提交报价数推导；不继续依赖经理方案状态。新业务页面询盘只三状态。
2. 保存作者、提交者、实际修改者分开，已提交同部门修改不冒用原作者；除作者可编辑之外，不擅自增加需求没规定的部门内草稿查看规则。销售无论列表、详情、导出、附件都不能看到未提交内容。
3. 询盘版本/轮次若用内部字段，应只防止撤回前旧客户端把旧数据写回，不显示额外业务状态或让用户增加版本选择步骤。事务内检查tenant、case、有效轮和权限；不要只在事务外查后直接插入。
4. 同库两部门报价与询盘撤回可使用同一根行锁，提交/保存/修改/撤回遵循同一锁顺序。唯一键/幂等用于防重复，无额外业务审批。跨export不能用“先异步删，再允许已确认合同丢失”的方式实现。
5. D1开始时先枚举export现有报价/合同怎样指向sourcing case/selection；对新D1接收用实时有效性过滤，旧export未确认报价需可靠失效清除。跨服务失败时不宣告撤回成功；具体同步命令或outbox补偿方案经调用核查后落地，但必须证明客户确认/合同形成与撤回互斥。不能凭仅检查一次合同数量就声称并发安全。
6. 不对现存所有RFQ/方案/旧报价批量删除，也不自动给所有旧资料标为新“已提交”。隔离历史样本区分未确认轮/已有合同引用后再写可审核的兼容映射。模糊记录列异常，不猜业务状态。
7. 采购报价及费用原币种保留，小计使用decimal，不经JS浮点作为账务真值。多币种分别合计；无已确认汇率时不强制合并。D1不抢跑五公式。
8. 工厂或货代手输采用业务对象快照/既有自由输入能力，不要求为了报价先新增主数据。已有工厂选择仍校验tenant与访问权限；不要删除主数据服务中的独立维护功能。

## 5. 技术验证与旧测试处置

- 前端：本worktree执行依赖锁定安装，`npm run typecheck`、`npm run build`、`npm test`；有意义测试覆盖可见性、分页粘贴和源报价只读。类型检查/构建不能替代跨模块验证。
- 后端：procurement业务与gRPC、gateway授权/DTO、export撤回保护、IAM范围相关测试；隔离DSN下运行数据库事务/并发用例，不接受skip作为通过。按实际改动跑proto生成、sqlc一致性、重复路由、权限种子、迁移安全及相关lint。
- 现有 `sourcing_handoff_integration_test.go` 断言接单/退回销售补资料版本流程，需按已取消业务重写断言；`customer_selection`强制先最终复询的测试D2替代；不为让旧测试变绿保留旧门槛。
- 旧银行删除/恢复等测试不作为D1验收要求；后续退役时用“独立旧写入口不可用、历史收付冲销凭证仍可用”的用例替换。不能为了旧测试保留银行流水业务。
- 仍有价值的来源归属、tenant隔离、重复请求、金额精度、文件和历史快照测试继续保留；不把整个旧测试目录一并删除。
- 各用例记录实际commit、角色、数据ID、操作/API、来源和接收结果、失败/未测、截图/日志证据。局部模拟测试仅记局部通过；真实链路断一处就不能标跨模块通过。
