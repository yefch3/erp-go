## 0. 使用方式与实施边界

原需求清单按模块回答“需要什么”；本文按业务流程回答“依赖什么、一起改哪里、如何证明接通”。不能以模块章节顺序作为开发顺序，也不能因页面可用就宣告跨模块完成。

- ⬜ 每次开始前，指定本文的一段流程，以及实际允许修改的页面、接口和相关接收逻辑。
- ⬜ 对照代码确认前置依赖是否真实可用；已有且满足需求的能力可复用，不因所属模块尚未整体验收就重写。
- ⬜ 功能范围外的旧能力不得继续暴露在本次重构模块中；检查其公共依赖，避免删坏范围外业务。
- ⬜ 必要内部实现不等同于新增业务功能；不得借依赖建设新增原需求没有的用户页面、操作或状态。
- ⬜ 业务差异按第 6 节核对；只暂停受影响的实施或验收，不阻塞其他明确部分。
- ⬜ 下列阶段是建议的依赖组织，不是已批准工期、完成记录或一次性修改授权。

## 1. 依赖总览

```text
核查代码、原业务权限和依赖
销售询盘 → 采购 / 物流售前询价 → 报价回传
人工确认有效汇率 + 售前报价 → 客户报价计算、调整、PDF
客户确认 → 外销合同上级确认、签署、上传、开始执行
→ 财务入账 → 财务确认执行条件

采购线（在现有采购订单页面中处理）：
正式采购需求 → 重新询价（可换工厂）
→ 确定各产品最终工厂、价格和条件 → 按最终工厂生成采购订单
→ 采购上级确认 → 签署并上传采购合同 → 财务上级或老板核验
→ 申请采购付款 → 财务出账 → 付款结果回传

物流线（在正式船期任务详情中处理）：
运输需求进入正式船期任务 → 重新询价（可换货代或实际承运船公司）
→ 确定最终货代、船公司、方案、费用和条件
→ 物流上级确认 → 签署并上传货代合同 → 财务上级或老板核验
→ 申请物流付款 → 财务出账 → 付款结果回传

两条线分别推进，不要求采购和物流互相等待才能申请付款。
采购按合同条件执行 → 备货完成 → 质检 / 复检 → 合格货物进仓和发货
物流按合同条件执行 → 订舱、进仓、报关、开船、到港
船期变化 → 采购暂缓发货提醒 / 财务资金提醒 / 相关人员查看
各阶段原业务状态和提醒 → 对应权限下的“我的待办”
历史执行中合同 → 接续原历史进度，不重走已完成业务
```

图中顺序用于说明依赖，不覆盖合同条件：允许先订舱后付款的货代合同不得被强制阻塞；采购执行以采购合同条件为准。质检合格影响相关货物发货，不意味着订舱必须等待全部质检结束。详见原需求及第 6 节差异。

### 1.1 必须区分的依赖

| 类别 | 检查内容 | 对实施和测试的影响 |
|---|---|---|
| 数据依赖 | 来源单据、产品明细、选定工厂/方案、金额与币种、历史进度 | 验证实际关联及带入数据，不能仅测试页面跳转 |
| 状态依赖 | 提交、撤回、客户确认、签署、核验、财务放行、质检结果 | 验证允许和禁止的操作，不仅验证正常顺序 |
| 权限依赖 | 负责销售、上级、部门人员、财务及质检角色 | 分别检查查看、修改与跨模块读取，待办不扩大权限 |
| 回传依赖 | 报价更新、付款结果、备货变化、质检结果、提醒处理 | 来源变化后，接收页面与待办必须符合原业务结果 |
| 历史依赖 | 已签合同、已执行数量、已收付款和已有船期 | 接续未完成部分，不能因重构重复产生已完成业务 |

### 实单重新询价与对象更换规则（本次修订）

1. 售前工厂报价、货代报价和运输方案作为参考，不锁定实单最终对象。
2. 财务确认具备执行条件后，采购和物流分别重新询价；允许更换工厂、货代公司或实际承运船公司。
3. 采购重新询价在现有“采购订单”页面内处理，不新增独立模块或页面。确定各产品最终工厂及价格后，按最终工厂生成采购订单；订单号仍与对应销售系统合同号一致。
4. 正式船期任务可以先承接运输需求，最终货代、船公司、费用和船期在重新询价中确定，不把售前对象作为不可更改的签约对象。
5. 货代公司与实际承运船公司分别记录：仅更换船公司不等于更换货代合同的签约和收款对象；货代仍是本需求中货代合同及相应付款申请的对象。
6. 提交上级确认的内容包含最终对象及其完整报价、交期或船期、付款条件。更换后不能继续把原对象的价格、合同、附件或账户当作新对象资料使用；保留的原资料只能作为原对象参考。
7. 后续合同、核验、付款申请、备货、质检和运输读取最终确认的正确对象及关联数据。仅内部重新询价或更换对象，不自动改写已确认的客户报价和外销合同。
8. 已签署或已付款后的对象变更不属于本次允许范围，不能据此覆盖历史合同和收付款记录；原文尚未明确的后续变更流程仍待核对。
9. 不因本次修订增加额外审批层级或业务状态。采购页面现有“待确认工厂报价”阶段包含实单重新询价，询价完成后再形成按工厂拆分的订单。

### 3.1 尚需代码核查或业务明确的交互细节

- ⬜ 检查各业务实际使用何种内部关联方式。特别是一份销售合同拆出的多个采购订单展示同一订单号时，必须验证不会把不同工厂的产品、付款或质检串到一起；不自行修改原需求规定的展示编号。
- ⬜ 原需求同时允许修改已提交报价、由客户确认报价建立合同；客户确认后修改来源报价如何影响已形成合同，未完整展开。先检查当前行为并列明差异，不擅自规定覆盖或冻结规则。
- ⬜ 多工厂和多个候选运输方案已明确，但客户最终选择多个方案时如何对应正式运输任务、各批数量，需核对当前实现及原需求是否足以确定；不能把所有候选方案自动当成已选实单。
- ⬜ 检查业务失败或同时操作时，如何避免重复正式单据、重复付款登记及残留报价。技术保障不增加业务状态；无法确定的业务冲突处理方式列出待核对。
- ⬜ 检查历史已收付记录、差额完成与冲销怎样回传未收/未付和相关提醒。原文没有明确的联动后果不能静默补定。
- ⬜ 财务核验未通过如何处理、可执行条件是否允许撤销、整份合同完成的具体判定等，原文未充分展开；遇到时记录待明确事项，不新增按钮或审批流。

## 4. 每段流程的跨模块验收

> 所有验收均需实际环境中的来源与接收实现共同参与。模拟接口可用于局部测试，但不能作为联动已通过的证据。测试数据用于验证规则，不是新增业务字段或产品功能。

### 4.1 D1：询盘与报价回传

- ⬜ 用负责销售提交含多个产品的询盘，分别以采购和物流账号核对产品、规格、数量和运输信息，以及销售客户报价入口。
- ⬜ 两名采购分别提交不同工厂报价，至少覆盖“部分产品”；物流提交同一货代的两个运输方案；销售看到正确来源与内容。
- ⬜ 保存但未提交的报价，销售不可见；填写人可编辑；提交后同部门有权限人员修改，销售看到更新及真实操作记录。
- ⬜ 原销售撤回后，采购和物流不能继续报价，已提交和未提交报价按原文清除，未确认客户报价同步清除。
- ⬜ 使用撤回前已打开的采购/物流页面再次尝试提交，不能重新留下已撤回询盘的有效报价。
- ⬜ 修改数量后重新提交，两边收到新需求；旧报价不恢复；其他普通销售不能越权查看或撤回。

### 4.2 D2：客户报价与外销合同

- ⬜ 对五条原文公式分别使用可手工核算的数据，核对人工确认汇率、费用、天数及两位小数结果。
- ⬜ 不同产品选不同工厂、PDF 放多个运输方案，确认 PDF 不泄露内部公式；销售手动调整的最终价格正确保留。
- ⬜ 客户确认后进入正确外销合同，字段不丢失；再尝试撤回询盘被阻止，不能清除已形成合同。
- ⬜ 新合同先提交上级；退回后改原合同并重提；同意后签署上传、开始执行；不能跳过原文规定的条件。
- ⬜ 来源报价在客户确认后的修改影响，按第 3.1 节核对后的明确规则验证，未明确前不得宣称全部通过。

### 4.3 D3：财务放行与实单生成

- ⬜ 合同在已核对的时点进入入账；尚未财务确认执行条件时，不进入正式采购和运输流程。
- ⬜ 分别验证收到预付款、收到信用证、无需预付款、特殊情况允许执行四条路径。

> **【本次修改 M08】以下为本次新增或调整内容：第 4.3 节：放行后不锁定售前对象的验收。**

- ⬜ 财务放行后，采购页面接收采购需求，船期接收运输需求；售前工厂、货代与船公司仅作参考，不锁定最终对象。
- ⬜ 重复点击、刷新或请求重试不导致同一触发结果被重复建立；发现已有重复时记录问题，不未经检查删除历史单据。
- ⬜ 销售仅看到是否可以执行，不能通过详情或关联接口读取原文禁止的收款金额及明细。


> **【本次修改 M09】以下为本次新增或调整内容：第 4.4 节：标题调整及新增的前五条更换对象验收项；后续原有用例保留。**

### 4.4 D4：重新询价、最终对象、合同核验及付款回传

- ⬜ 采购由售前工厂甲改选工厂乙，或调整多个产品的工厂分配，按最终工厂拆单；订单产品、报价、合同和付款对象正确，展示编号仍符合原需求。
- ⬜ 物流更换货代后，最终报价、货代合同、核验资料和付款对象关联新货代，不沿用旧货代账户或附件。
- ⬜ 仅更换实际承运船公司而货代不变时，运输信息更新，不能误把货代合同和收款对象变成船公司。
- ⬜ 新对象报价不得自动继承旧对象价格或付款资料；原资料保留时明确属于原对象，仅供参考。
- ⬜ 内部重新询价和更换对象不自动覆盖已确认客户报价、外销合同及历史已签已付记录。


- ⬜ 采购和物流各自完成最终条件确认、上级退回修改及同意路径，核验通过前不能申请付款。
- ⬜ 使用财务上级或老板账号核验正确签署合同，不能把采购合同与货代合同或其他订单的附件混用。
- ⬜ 两类付款申请进入同一出账页面，业务单号、收款方、金额、币种、账户、附件和申请人正确。
- ⬜ 分两次付款，分别核对出账及原业务的已付、未付和付款结果；超付被拒绝，冲销后结果按原需求重新计算。
- ⬜ 原模块提供的数据与财务展示一致；采购、物流不能修改财务付款记录。
- ⬜ 以允许先订舱后付款的合同验证订舱可按条件继续；采购执行条件同样按合同约定核查，不强制套用单一付款门槛。

### 4.5 D5：备货、质检与发货

- ⬜ 采购更新预计/实际备货，船期读取同步结果且不可改写采购数据；生产或备货完成按核对后的规则产生质检任务。
- ⬜ 多产品任务分别填写数量、结果、问题与报告，验证全合格、部分合格和不合格三种路径。
- ⬜ 全合格后采购和物流看到正确结果；部分合格时采购决定合格部分是否先发；不合格部分不能被当成可发货数量。
- ⬜ 异常到采购经理，复检发生在同一任务，旧照片及报告仍可查看；新合格结果同步原采购和船期业务。
- ⬜ 已完成质检不能重新打开修改结果，只按原文查看、下载及补附件；相关角色报告访问范围正确。
- ⬜ 不将“所有货物全部合格”错误设为合格部分发货的统一前提，不新增免检流程。

### 4.6 D6：运输与提醒闭环

- ⬜ 物流订单完成审批、签约并进入“已委托”后建立正式船期；不增加独立宣船页面、宣船状态或额外审批。
- ⬜ 当前一份外销合同只建立一条有效正式船期，不提供拆分运输批次、分批发运或累计发运数量计算；重复建立必须被阻止。
- ⬜ 建立及后续维护正式船期时可填写或补录船公司、船名、航次、订舱号和提单号；暂不能确定的字段允许留空并在后续节点补充。
- ⬜ 同一正式船期维护进仓日期、报关日期、ETD、ETA、实际开船日期、实际到港日期、运输附件和备注；换船或日期变化更新原记录并保留变更历史，不新建运输批次。
- ⬜ 待订舱、待开船、运输中和已到港的操作与正式船期详情一致；物流订单、船期管理及待办跳转到同一业务记录，不生成重复执行页面。
- ⬜ ETA 提前时，对应出账和船期出现提醒；按实际系统设置判断紧急；财务“已准备”只反馈处理结果，不冒充已付款。
- ⬜ 实际付款完成后提醒结束；货物实际提前到港且尚未处理时再次提醒。
- ⬜ 未开航 ETD 或进仓日期延后时通知相关采购，采购确认“已通知工厂”，新日期可用于后续安排。
- ⬜ 已开航仅 ETA 延后，不向工厂发送停止发货要求；相关人员看到最新日期及提醒。
- ⬜ 预计开船、预计到港、实际开船、实际到港、提前到港、延误和付款准备提醒显示在原业务页面、对应财务记录及相关待办中，不新增独立提醒模块。
- ⬜ 各用户可分别设置各类提醒提前天数，设置不改写业务日期或其他用户配置；按用户业务时区跳过周六、周日。
- ⬜ 物流和财务可以查看船期资料、运输附件及物流费用；采购、相关销售及上级只查看权限范围内的运输节点、日期、状态和提醒，不查看船期附件及物流费用；待办本身不授予额外业务权限。
- ⬜ 提醒不产生原文没有的业务状态、独立业务页面或额外审批。
- ⬜ 用户业务时区未配置时明确提示，不得把开发环境日期或代码默认值写成业务规则；本阶段不接入 Google Calendar 或国际公共节假日。
- ⬜ 五公式输入口径、物流费用分摊，以及 D5 暂缓的质检结果通知采购、采购端查看质检资料和部分合格先发流程继续作为待确认项，不因进入 D6 自动扩展范围。

### 4.7 D7：历史接续及独立财务

- ⬜ 录入含已执行与未执行部分的历史合同、已收款和已付费用，验证只继续剩余业务且不重复走历史审批签字。
- ⬜ 历史采购和船期按已有工厂及船期接续；相同展示单号不造成工厂、金额或运输批次串单。
- ⬜ 手工添加收付款支持原文规定的选择和手输，分次收付、差额完成、撤销完成及冲销按原需求工作。
- ⬜ 多币种分别展示合计；形成单一总额时使用业务默认结算币种；禁止正常登记超收超付，退款通过反向冲销。

> **【本次修改 M10】以下为本次新增或调整内容：第 4.7 节：替换原银行流水验收项，验证入口退出和凭证保留。**

- ⬜ 财务只保留入账、出账、汇率；所有收支通过入账或出账登记，不另建银行流水；原有独立流水入口与写操作退出本次财务功能，收付款账户和回单/凭证仍可使用。
- ⬜ 出差付款及筛选按照核对后的原文范围验收，不自行删除出差需求或增加未确定筛选项。

### 4.8 T：待办与权限，随每段接入

- ⬜ 当前阶段原业务产生需处理事项后，正确角色看到对应待办；业务单号、当前状态、来源和详情跳转一致。
- ⬜ 原业务完成后待办自动完成；下一处理事项及退回修改待办按原业务产生；不能用待办按钮简单关闭业务。
- ⬜ 已完成待办仅查历史，不从中修改已完成业务；紧急程度读取原设置阈值。
- ⬜ 在不同角色账号下验证列表、详情、附件及操作权限；收到待办不授予额外业务权限。
- ⬜ 尚未实现或尚无真实来源的待办类型列为缺口，不用固定样例冒充已接通。

| 角色权限、详情入口或原业务状态 | 相关业务列表、详情、修改、附件与待办聚合/跳转，不只测试菜单 | I01～I18 中受影响部分 |

- ⬜ 对上述受影响链路按实际改动选择回归用例，不机械重测所有模块，也不只测改动页面。
- ⬜ 对撤回与报价提交、重复点击或重试、跨模块写入失败，检查是否留下与原需求矛盾的数据；如未验证，明确记录剩余风险。
- ⬜ 涉及持久数据结构修改时核查已有数据如何继续使用；技术迁移或兼容处理不能擅自改变原业务规则。
