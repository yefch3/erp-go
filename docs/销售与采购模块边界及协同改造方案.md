# 销售与采购模块边界及协同改造方案

> 方案日期：2026-08-27。
> 本文档只定义模块归属、协同流程、权限和分阶段改造顺序，暂不修改现有业务代码。
> 原则：保留已经可用的功能、流程和操作按钮；优先调整入口、页面视角和权限边界，不复制业务数据。

## 0. 结论

当前系统真正的问题不是功能做错了，而是把一条跨部门流程全部放进了“采购管理”：

```text
客户询盘 → 人工复核 → 工厂询价 → 供应商报价比较 → 成本确认
        → 客户报价 → 客户接受/拒绝 → 出口合同 → 采购需求 → 采购单
```

其中前半段和后半段本来就需要销售、采购共同完成。建议改成：

- **销售负责客户侧**：接收客户需求、确认客户资料、跟踪采购进度、制作并跟踪客户报价、形成出口合同。
- **采购负责供应商侧**：接收销售提交的采购寻源任务、联系供应商/工厂、比较供应商报价、确认采购成本、创建并执行采购订单。
- **系统负责交接**：同一业务案件只保存一份数据，通过明确的“提交采购寻源”“成本方案已确认”“客户接受/拒绝”等节点让两个模块联动。
- **不把同一页面复制两份**：销售和采购进入同一个案件，但看到不同的页签、字段和可操作按钮。

一句话边界：

```text
对客户说什么、卖多少钱，由销售负责；
向哪家供应商买、采购成本多少，由采购负责。
```

## 1. 当前系统检查结果

### 1.1 当前销售菜单

当前销售菜单只有：

- 出口合同
- 执行一览

客户询盘、客户报价没有独立销售入口。

### 1.2 当前采购菜单

当前采购菜单包括：

- 采购工作台
- 待复核询盘
- 询价案件
- 询盘模板
- 待采购
- 采购订单

其中“待复核询盘”“询盘模板”和“询价案件”中的部分能力实际属于销售。

### 1.3 当前询价案件混合了两类职责

当前询价案件详情包含：

1. 已审核询盘
2. 工厂询价
3. 报价比较
4. 成本方案
5. 报价单
6. 变更记录

前四项主要是需求交接和采购寻源，第五项“客户报价”是销售工作。当前还存在以下权限耦合：

- `procurement:sourcing:*` 控制询盘、工厂 RFQ、供应商报价和成本方案。
- “生成客户报价”同时要求采购审批权限和 `export:quotation:write`。
- 销售只有客户报价、合同权限时，没有独立入口查看自己询盘的采购进度。

因此，当前普通销售无法完整管理自己的客户询盘；采购经理又被迫承担“生成客户报价”的销售动作。

## 2. 功能归属清单

### 2.1 应归销售模块

| 当前功能 | 建议归属 | 原因 |
|---|---|---|
| 询盘模板 | 销售－询盘设置 | 这是客户需求标准化格式，不是供应商 RFQ 模板 |
| 邮件转入标准询盘 | 销售－待复核询盘 | 来源是客户邮件，客户和联系人由销售确认 |
| 手工上传标准询盘 | 销售－待复核询盘 | 本质是销售录入客户需求 |
| 待复核询盘 | 销售－待复核询盘 | 销售确认客户原始需求是否准确、是否值得继续 |
| 已审核询盘/客户需求 | 销售－询盘项目 | 是销售提交给采购的需求快照 |
| 客户报价单 | 销售－客户报价 | 面向客户的价格、有效期、发送和反馈由销售负责 |
| 客户接受/拒绝 | 销售－客户报价 | 客户反馈只能由销售记录和解释 |
| 报价被拒后的反馈 | 销售－询盘项目 | 销售记录客户真正的调整要求，再发给采购 |
| 出口合同 | 销售－出口合同 | 保持现状 |
| 执行一览 | 销售－执行一览 | 保持现状；我的待办只跳转，不搬走页面 |

### 2.2 应归采购模块

| 当前功能 | 建议归属 | 原因 |
|---|---|---|
| 采购工作台 | 采购－采购工作台 | 采购人员的任务入口 |
| 工厂询价/RFQ | 采购－采购寻源 | 面向供应商和工厂 |
| 供应商联系人、回复期限 | 采购－采购寻源 | 属于供应商沟通记录 |
| 下载工厂询价单 | 采购－采购寻源 | 面向供应商 |
| 手工录入/导入供应商报价 | 采购－采购寻源 | 采购价格资料 |
| 供应商报价比较 | 采购－采购寻源 | 比较价格、MOQ、周期、付款条件 |
| 成本方案 | 采购－采购寻源 | 确认供应商选择及采购成本基础 |
| 确认成本方案（中标） | 采购经理/授权审批人 | 对采购选择负责 |
| 待采购 | 采购－待采购 | 只放客户成交或例外采购产生的真实采购需求 |
| 采购订单与审批 | 采购－采购订单 | 保持现状 |
| 发供应商采购单、交付跟踪 | 采购－采购订单 | 保持现状 |

### 2.3 需要共享、但只能有一份的数据

| 共享内容 | 主责方 | 另一方看到什么 |
|---|---|---|
| 客户需求和产品明细 | 销售 | 采购看到提交时的只读版本快照 |
| 采购寻源进度 | 采购 | 销售看到“待接单/询价中/待确认成本/已完成/异常”，不直接改采购记录 |
| 供应商和采购单价 | 采购 | 默认不向普通销售显示供应商底价；有专门价格权限才显示 |
| 已确认成本依据 | 采购经理 | 销售看到可用于报价的成本版本和建议售价信息 |
| 客户报价 | 销售 | 采购只看到“草稿/已发送/接受/拒绝”，不操作客户反馈 |
| 客户拒绝原因 | 销售 | 采购看到结构化调整要求，用于新一轮询价或成本版本 |
| 出口合同结果 | 销售 | 采购看到采购需求及交付方式，不修改合同 |
| 采购订单/到货进度 | 采购 | 销售在执行一览中看到进度摘要，不修改订单 |
| 变更记录 | 系统 | 双方按权限查看同一条时间线 |

## 3. 目标菜单结构

### 3.1 销售模块

```text
销售
├─ 销售工作台（后续阶段，可先不做）
├─ 待复核询盘
├─ 客户询盘项目
├─ 客户报价
├─ 出口合同
└─ 执行一览
```

建议名称说明：

- 当前“询价案件”在销售侧显示为“客户询盘项目”。
- “客户报价”恢复为销售独立入口，但仍可从询盘项目直接进入对应报价。
- 当前“询盘模板”移到销售下的“询盘设置”或系统设置，不再显示在采购菜单。

### 3.2 采购模块

```text
采购管理
├─ 采购工作台
├─ 待开始询价
├─ 全部寻源项目
├─ 待采购
└─ 采购订单
```

建议名称说明：

- “待开始询价”是销售已提交、采购尚未创建首条工厂询价的客户需求，不等同于“待采购”。
- “全部寻源项目”包含待开始、询价中、比价中和成本方案中的所有寻源案件。
- “待采购”只放成交后等待生成采购单的真实需求，名称和逻辑保持现状。

### 3.3 不建议做的拆分

- 不新建一套销售询盘表和一套采购询价表。
- 不复制“询价案件详情页”形成两个互不关联的副本。
- 不让销售直接修改供应商报价，也不让采购直接记录客户接受/拒绝。
- 不因为菜单移动就修改已经验证通过的业务按钮和状态机。

## 4. 同一案件的两个页面视角

底层继续使用同一个 `sourcing_case` 和同一个案件号，例如 `SC-20260827-000013`。

### 4.1 销售视角：客户询盘项目详情

建议页签：

1. **客户需求**：当前“已审核询盘”，显示客户、联系人、需求明细和来源邮件。
2. **采购进度**：只读显示采购是否接单、已询价供应商数量、回复完成度、预计完成日和异常。
3. **报价依据**：显示采购已提交给销售的成本版本；敏感字段按权限隐藏。
4. **客户报价**：打开、编辑、下载、发送、客户接受、客户拒绝。
5. **变更记录**：客户需求变更、采购交接、报价反馈的统一时间线。

销售侧主要按钮：

- 保存询盘草稿
- 提交采购寻源
- 修改后重新提交
- 查看采购进度
- 生成/打开客户报价
- 下载/发送报价
- 客户接受
- 客户拒绝
- 查看来源邮件

### 4.2 采购视角：采购寻源项目详情

建议页签：

1. **需求快照**：销售提交的客户需求，只读；如有问题使用“退回补充”，不能直接改客户需求。
2. **工厂询价**：保留当前 RFQ 功能和操作下拉。
3. **报价比较**：保留当前价格、MOQ、生产周期、付款条件比较。
4. **成本方案**：保留当前费用、汇率、利润规则和确认成本功能。
5. **变更记录**：显示采购相关操作和销售交接事件。

采购侧主要按钮：

- 接受任务
- 退回补充
- 新增工厂询价
- 下载询价单
- 修改询价记录
- 录入/导入供应商报价
- 新建成本方案
- 确认成本方案
- 提交给销售报价

### 4.3 双角色用户

同时拥有销售和采购权限的员工：

- 两个菜单都显示。
- 从销售入口进入时默认打开销售视角；从采购入口进入时默认打开采购视角。
- 页面提供“查看采购寻源 / 查看客户询盘”跨模块链接。
- 链接只切换视角，不复制案件，也不改变当前状态。

## 5. 销售与采购的准确交互流程

### 5.1 正常流程

```text
销售：接收并复核客户询盘
  ↓ 点击“提交采购寻源”
系统：冻结需求版本 V1，生成采购寻源任务
  ↓
采购：接单 → 工厂询价 → 录入报价 → 比价 → 成本方案
  ↓ 点击“确认成本方案”
采购确认成本版本 Cn
  ↓ 点击“提交销售”
系统：冻结成本版本 C1，通知销售
  ↓
销售：基于 C1 生成客户报价 Q1 → 发送客户
  ├─ 客户接受 → 销售形成合同 → 系统生成采购需求 → 采购制单
  └─ 客户拒绝 → 销售记录原因 → 发起调整请求 → 采购建立 C2
```

### 5.2 为什么必须冻结版本

销售提交后，采购不能面对一份随时变化的客户需求；采购确认成本后，销售也不能面对随时变化的采购底稿。

因此每次交接必须保存快照：

- 需求版本：`V1 / V2 / V3`
- 成本方案版本：`C1 / C2 / C3`
- 客户报价版本：`Q1 / Q2 / Q3`

关联关系示例：

```text
需求 V2 → 成本 C2 → 客户报价 Q2
```

旧版本不删除，只标记为已取代，确保半年后仍能解释当时为什么采用某家供应商和某个价格。

### 5.3 客户拒绝后的处理

客户拒绝不能直接把已确认成本改回草稿。正确流程：

1. 销售在客户报价中选择“客户拒绝”。
2. 填写简短反馈，例如价格、交期、付款条件、规格变更或暂缓。
3. 系统保留原报价和原成本方案。
4. 如需采购重新处理，销售点击“发起调整请求”。
5. 采购基于原方案创建新版本，不覆盖历史。

### 5.4 客户需求变更

采购已经接单后，销售不能直接覆盖产品、数量、港口或交期：

- 销售提交“需求变更”。
- 系统展示变更前后差异。
- 采购确认影响：继续原 RFQ、补充 RFQ、取消部分 RFQ 或重新询价。
- 新成本方案必须关联新的需求版本。

### 5.5 采购退回补充

采购发现规格、数量、港口等信息不足时：

- 点击“退回补充”。
- 必须选择缺失项并填写简短说明。
- 销售收到待办，补充后重新提交。
- 采购原有记录保留，但在重新提交前不能确认新成本方案。

### 5.6 客户接受后的采购启动条件

仅“客户接受报价”还不一定等于立即下采购单。建议沿用现有规则：

```text
客户接受报价 → 生成/提交出口合同 → 合同审批并生效
              → 系统生成真实采购需求 → 进入“待采购”
```

这样未生效合同不会污染真实采购缺口。

交付方式也必须随合同保存快照：

- **直接交付**：采购需求和采购单仍然生成，但后续不进入公司实际仓库收货。
- **进入仓库**：采购需求继续衔接待到货、收货登记和库存。
- 销售只选择合同交付意图；实际收货仓、到货和库存操作仍由采购/仓库负责。

## 6. 状态设计

### 6.1 不建议只用一个超长状态

一个 `status` 同时表达销售、采购和客户状态，会造成“采购已经完成，但案件仍显示客户报价中”的混乱。

建议逻辑上拆成三个并行状态，初期可以先由现有状态映射，不必马上改数据库：

| 状态组 | 示例状态 |
|---|---|
| 销售询盘状态 | 草稿、待补充、已提交采购、待客户确认、已成交、已关闭 |
| 采购寻源状态 | 待接单、询价中、待比价、成本测算中、已提交销售、已退回/已取消 |
| 客户报价状态 | 未生成、草稿、已发送、已接受、已拒绝、已作废 |

页面顶部显示角色最关心的状态，并在详情里展示完整链路。

### 6.2 现有状态的过渡映射

| 现有状态 | 销售侧显示 | 采购侧显示 |
|---|---|---|
| `INTAKE_PENDING` / `REVIEWING` | 待复核/待补充 | 尚未提交采购 |
| `SOURCING` | 采购处理中 | 工厂询价中 |
| `QUOTES_RECEIVED` | 采购处理中 | 待报价比较 |
| `COSTING` | 待采购提交方案 | 成本测算中 |
| `CUSTOMER_QUOTE_CREATED` | 客户报价处理中 | 已提交销售 |
| `CANCELLED` | 已结束 | 已结束 |

第一阶段只做显示映射和菜单拆分，降低改造风险；后续再补独立状态字段。

## 7. 权限与数据范围设计

### 7.1 销售权限建议

```text
sales:inquiry:read
sales:inquiry:write
sales:inquiry:submit
sales:procurement-progress:read
export:quotation:read
export:quotation:write
export:contract:read
export:contract:write
```

销售普通员工默认只看本人客户和本人询盘；销售经理按部门或全部范围查看。

#### 7.1.1 角色权限页面的分组名称

当前客户报价和出口合同权限使用 `export:*` 编码，并在角色权限页面归入“出口业务”。
这会让管理员误以为系统没有销售权限。SP2 应采用兼容方式调整：

- 后端现有 `export:*` 权限编码暂不重命名，避免破坏已经使用这些编码的接口和角色。
- 角色权限页面把 `export` 分组显示为“销售与出口”。
- 新增的客户询盘权限使用 `sales:*`，在页面显示为“销售”。
- 如果最终保留两个分组，页面顺序固定为“销售、销售与出口、采购”，并用说明文字明确边界。
- 不允许仅通过修改中文名称把采购权限伪装成销售权限。

#### 7.1.2 预置销售角色

当前代码会为新公司补齐采购专员、采购经理、物流和财务角色，但销售角色没有进入同一套
新公司预置逻辑。SP2 需要增加以下预置角色；只给新角色默认值，不覆盖管理员已经调整过的角色：

| 角色 | 默认职责 | 建议默认权限 | 默认数据范围 |
|---|---|---|---|
| 销售专员 `SALES` | 维护自己的客户询盘、客户报价和合同 | `sales:inquiry:read/write/submit`、`sales:procurement-progress:read`、`export:quotation:read/write`、`export:contract:read/write`、客户主数据只读 | 销售/出口业务 `SELF` |
| 销售经理 `SALES_MANAGER` | 管理团队销售业务、合同审批和负责人转移 | 销售专员全部权限，加 `export:contract:approve`、`export:ownership:transfer` | 默认 `DEPT_AND_SUB`；确有全公司职责时由管理员改为 `ALL` |

兼容现有 `SALES_RO` 的原则：

- 不直接删除或改名，避免现有员工突然失去权限。
- 升级时检测该角色是否存在及其实际授权，不覆盖客户自行修改过的配置。
- 角色若代表普通销售，可由管理员迁移成员到新的 `SALES`；确认无成员后再停用旧角色。
- 新租户只播种新的标准角色，旧编码只作为升级兼容。

#### 7.1.3 销售角色不应默认获得的权限

- 不授予 `procurement:sourcing:price`，避免普通销售查看或修改供应商底价。
- 不授予 `procurement:sourcing:approve`，销售不能确认采购中标方案。
- 不授予 `procurement:order:write/submit/send/cancel`，销售不能代采购制单或发单。
- 不授予仓库收货、库存调整和供应商付款权限。
- 销售查看采购结果统一走采购进度摘要及已确认报价依据，不用采购全量权限代替。

### 7.2 采购权限保留与调整

现有权限可以继续使用：

```text
procurement:sourcing:read
procurement:sourcing:write
procurement:sourcing:send
procurement:sourcing:price
procurement:sourcing:approve
procurement:requirement:read/write
procurement:order:read/write/submit/cancel/send/close
```

但应调整 `procurement:sourcing:approve` 的含义：

- 只负责确认采购成本和供应商选择。
- 不再代表“生成客户报价”。
- 生成、发送和记录客户反馈只由 `export:quotation:write` 控制。

### 7.3 跨模块只读权限

不要为了让销售看采购进度，就给销售完整的 `procurement:sourcing:read`；否则销售可能看到全部供应商底价和不属于自己的案件。

建议提供专用的只读摘要接口和权限：

```text
sales:procurement-progress:read
GET /api/sales-inquiries/{id}/procurement-progress
```

同理，采购查看客户需求时使用采购任务自带的需求快照，不需要获得全部客户报价写权限。

### 7.4 权限变化时页面如何自动调整

- 菜单由权限计算：没有销售询盘权限就不显示销售询盘入口。
- 页签由权限计算：销售只看到销售页签，采购只看到采购页签。
- 按钮由“权限 + 数据归属 + 当前状态”共同计算。
- 权限被管理员移除后，重新获取 `/api/me/permissions` 即更新菜单和动作。
- 后端接口必须再次校验，不能只靠前端隐藏。
- 空权限不会留下奇怪的空卡片；整个分组没有可见内容时直接隐藏分组。

## 8. 系统交接协议

### 8.1 建议的业务事件

| 事件 | 发起方 | 接收方 | 系统动作 |
|---|---|---|---|
| `SALES_INQUIRY_SUBMITTED` | 销售 | 采购 | 冻结需求版本，生成待采购寻源任务 |
| `SOURCING_RETURNED` | 采购 | 销售 | 生成补充资料待办 |
| `PROCUREMENT_COST_CONFIRMED` | 采购经理 | 销售 | 冻结成本版本，生成客户报价待办 |
| `CUSTOMER_QUOTE_SENT` | 销售 | 采购（只读） | 更新采购侧客户状态摘要 |
| `CUSTOMER_QUOTE_REJECTED` | 销售 | 采购 | 保存反馈，可发起新成本版本 |
| `CUSTOMER_QUOTE_ACCEPTED` | 销售 | 合同流程 | 允许创建出口合同 |
| `CONTRACT_EFFECTIVE` | 合同审批 | 采购 | 按合同生成采购需求 |
| `PURCHASE_PROGRESS_CHANGED` | 采购 | 销售 | 更新执行一览和我的待办摘要 |

### 8.2 事件要求

- 每个事件带租户、案件 ID、业务版本、操作人和时间。
- 必须幂等，重复消息不能生成两条采购任务、报价或采购需求。
- 失败可重试，并在变更记录中留下结果。
- 跨服务只传 ID 和必要快照，不允许一个服务直接修改另一个服务的核心表。

## 11. 验收清单

### 11.1 普通销售

- [ ] 能复核自己的客户询盘并提交采购。
- [ ] 不能看其他销售的询盘（除非数据范围允许）。
- [ ] 能看采购进度摘要，但默认看不到供应商底价。
- [ ] 能生成、发送和跟踪自己的客户报价。
- [ ] 不能创建 RFQ、录供应商报价或确认采购成本。

### 11.2 销售经理

- [ ] 能按配置的数据范围查看团队询盘和报价。
- [ ] 能查看团队的采购进度，但不能越权修改采购记录。

### 11.3 采购专员

- [ ] 能接收销售提交的任务。
- [ ] 能退回不完整需求。
- [ ] 能创建 RFQ、录入/导入报价、比较报价并制作成本草稿。
- [ ] 不能发送客户报价或记录客户接受/拒绝。

### 11.4 采购经理

- [ ] 能确认供应商选择和成本方案。
- [ ] 确认后销售立即收到可报价待办。
- [ ] 没有销售报价权限时，不能替销售生成或发送客户报价。

### 11.5 跨模块闭环

- [ ] 同一案件在两个模块中保持同一个案件号。
- [ ] 销售修改已提交需求时必须产生新版本。
- [ ] 采购提交成本后，销售只能使用已确认版本生成报价。
- [ ] 客户拒绝不会覆盖历史成本和历史报价。
- [ ] 合同未生效前不会生成真实采购需求。
- [ ] 合同生效后只生成一次采购需求。
- [ ] 直接交付与进入仓库两条履约路径均正确。
- [ ] 权限调整后菜单、页签和按钮自动匹配，不出现空白模块或越权操作。

## 12. 开始改代码前需要业务确认的四点

1. 销售菜单中的名称采用“客户询盘项目”，采购菜单采用“采购寻源项目”。
2. “待复核询盘”由销售负责，不再作为采购日常入口。
3. 采购确认的是成本与供应商选择；销售决定最终客户报价并记录客户反馈。
4. 客户接受后仍以“合同审批生效”作为生成采购需求的唯一触发点。

以上四点确认后，建议先实施 **SP1（菜单和双视角）**，不要一开始就重构数据库和服务。
