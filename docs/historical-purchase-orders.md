# 历史采购单补录

采购订单右上角提供「补录历史采购单」。使用现有采购建单权限和采购订单 Data Scope，供应商沿用现有主数据访问校验，所有数据按登录上下文 tenant_id 隔离。

- 必填原下单日期、产品名称、数量和单位。供应商选填，留空也可保存草稿或确认补录；有供应商时仍须选择当前账号可访问的有效供应商。原单号可留空自动生成，同公司重复单号拒绝。
- 保存草稿后可继续补录；确认补录进入 ORDERED，不发起新采购审批，不生成收货、库存或付款记录。
- 使用现有采购订单、产品行及附件表。历史元数据单独记录原日期、录入人和真实录入时间。为兼容现有需求外键，每行有一条已关闭的内部手工需求，不进入待采购队列，不关联客户报价或采购批次。
- 默认直接送达，收货地址可补填；本入口用于补录仍待履约的历史订单，不用于追溯生成已发生的库存和付款。
- 未填写单价通过 price_missing 与 prices_complete 明确区分；订单列表/详情不将未知价格显示为零。补齐前拒绝登记到货和申请付款。
- 已确认且未到货的单据可通过「补齐资料 / 价格」补填空缺供应商、资料和价格；已有供应商不能更换或清空，币种、产品或数量不能改变。供应商和价格补齐前不能登记到货或申请付款；申请付款后停止编辑。
- 上传原合同或订单文件复用采购资料，单个上限 10 MB。草稿保存后上传，再确认，上传失败可在同一草稿重试。
- 补录订单可进入现有质检来源列表，质检仍在同一订单下记录。

部署先执行采购迁移 00075，再更新采购服务、网关和前端。

验证：数据库集成测试覆盖草稿/确认、补价、金额、跨 tenant 拒绝、负责人范围、重复单号、原审批入口拦截、附件、质检衔接及不产生待采购需求/收货记录；同时回归现有质检测试、Go 测试及 Vue 类型检查和构建。

补录表单与正常单据对齐：移除联系人、联系电话、收货地址；预计到货与应付到期日使用现有订单字段，采购员默认是录入人（可改，见下文「采购员」），金额汇总计算。产品支持现有目录选择并保存产品 ID、编码、单位关联，旧产品未建档时可输入历史名称。

Excel 明细导入：提供固定表头模板，支持 .xlsx/.xls；仅向当前草稿追加产品行，不自动建单。产品名称、数量、单位必填，价格可空；错误行显示原行号，正确行保留。供应商、原下单日期等单头信息仍由页面填写，权限和 tenant_id 继续在保存接口检查。总金额未齐时显示为空。

补录窗口不再显示应付到期日；产品明细采用横线分隔的紧凑行，无独立输入边框，聚焦时显示底线提示。已有应付日期在编辑时仍保留，不因移除输入项而清空。

## 采购员：补录时可选，录完可换（#643）

采购订单按采购员决定谁看得见。历史补录的单以前一律记在录入人名下、换不了，于是一个人统一补录的单，「只看得到自己单子」的采购同事一张都找不到，供应商和价格也没人能补。

- **补录时选**：补录窗口里「采购员」是下拉，默认录入人自己，可以选真正负责的同事。保存的顺序不变（先存单、传附件、确认），**最后一步**才把单子换给选中的人——换出去之后，录入人可能就看不到这张单了，前面几步都做不了。换人这一步失败不算保存失败：单子已经存好，提示里会说去「更多操作 → 更换采购员」再试。存草稿时选了同事，草稿同样交给对方，由对方继续补录。候选名单取不到时退回成只读框，照常记在录入人名下。
- **录完再换**：采购订单列表「更多操作 → 更换采购员」。只对历史补录的单提供（已取消的除外）；正常流程的单不能换——那里采购员同时是审批的发起人和草稿的所有者。
- **换给谁**：持有「维护采购订单」（`procurement:order:write`）、登得上来的在职同事。名单由 IAM 的 `ListPermissionHolders` 给出，认人的规则和 `CheckPermission` 是同一条（在职、角色启用），另加一条「有账号且没被停用」——挑到一个登不上来的人，单子就没人接得住。名单只有姓名和部门，对有这项权限的人都一样，不按各自的 Data Scope 裁。
- **谁能换**：有「维护采购订单」权限、并且看得见这张单的人。**不要求对方在自己的 Data Scope 里**——否则「仅本人」的录入人谁也给不了；给出去不泄露任何东西，因为他本来就看得见。看不见这张单的人得到的是「采购单不存在」。
- **换了之后**：单子上的采购员改成新的人，这张单每行那条内部手工需求的负责人、还没关闭的生产节点提醒一起跟着走；状态、供应商、价格、收货、付款都不动，录入人和录入时间也保留。已经登记的供应商发票、付款记录仍按**登记人**可见，不随采购员转移。之后别人再接着补录这张草稿，重建出来的内部需求仍归单子上的采购员，不归保存的人。
- **已知的小缝**：登记生产节点时提醒上的采购员是在事务外读的。同一瞬间一个人登记逾期节点、另一个人换采购员，新生成的那条提醒可能还写着原采购员（只影响执行页上这条提醒显示的名字）。
- **留痕**：每次真正的更换在 `purchase_order_buyer_changes` 留一行——原采购员、新采购员、原因（选填）、操作人、时间。换成现在这位不算更换，不留痕。

接口：`GET /api/purchase-orders/buyer-candidates`、`PUT /api/purchase-orders/{id}/buyer`（`{buyerId, reason}`），都要求 `procurement:order:read` 和 `procurement:order:write`。

部署：采购迁移 00090（只新增一张表，不改已有数据）；IAM、采购、网关、前端一起更新。采购服务取名单要调 IAM 的新接口，IAM 还没更新的那一小段时间里名单取不到，页面会退回只读框或提示「没有取到」，不影响保存。

验证：采购集成测试 `TestHistoricalOrderBuyerCanBeChosenAndChanged`（谁能换、换给谁、换完谁看得见、只动采购员、留痕、只对历史单开放），IAM 集成测试 `TestPermissionHoldersMatchCheckPermissionPersonByPerson`（名单和把关逐人一致），网关 `order_buyer_test.go`（路由、地址上的单号说了算、字段不丢），前端 `orderBuyer.test.ts`。
