# 供应商应付对账实现方案

> 对应 `docs/开发计划.md` 的 **A4**,以及采购需求清单 §8.2。
>
> 建立于 2026-08-20。**方案里的每一条现状都经过三层核验**(迁移、服务端、前端),
> 不采信需求清单里的 ✅/⬜ 标记。

---

## 一、这件事在讲谁欠谁

我们是外贸贸易公司,夹在中间,两侧方向相反:

```
   销售侧（应收）—— 已完成                 采购侧（应付）—— 本文档
   ────────────────────                  ────────────────────
   国外客户 ──下单──▶ 我们                我们 ──采购订单──▶ 工厂
   我们     ──发货──▶ 客户                工厂 ──发货────▶ 我们（收货单）
   客户     ──付汇──▶ 我们                工厂 ──发票────▶ 我们
                                          我们 ──付款────▶ 工厂
```

本文档只做右侧。**我们是买方,工厂是卖方。**

### 三单匹配里谁开给谁

| 单据 | 谁产生 | 性质 | 现状 |
|---|---|---|---|
| 采购订单 | **我们**开给工厂 | 我们的**承诺** | ✅ `purchase_orders` |
| 收货单 | **我们**自己记 | 我们看到的**事实** | ✅ `purchase_receipts` |
| 供应商发票 | **工厂**开给我们 | 对方的**索款** | ❌ 不存在 |

> **三单匹配的本质:拿我们的承诺 + 我们看到的事实,去校验对方的索款。**

前两单是我们自己的记录,第三单是外来的。所以第三单**是被校验的对象,不是依据**。

### 命名必须带方向

系统里已有销售侧,「订单」「发票」各有两个且含义相反。新表一律把方向写进名字:

| 概念 | 销售侧（已有） | 采购侧（本文档） |
|---|---|---|
| 单据 | `contracts` 客户欠我们 | `purchase_orders` 我们欠工厂 |
| 发票 | 我们开给客户 | `supplier_invoices` 工厂开给我们 |
| 钱 | `bank_transactions` CREDIT | `supplier_payments` |
| 核销 | `receipt_allocations` | `payment_allocations` |

## 二、现状核验

### 已经有的（比开发计划里写的多）

```
purchase_orders          currency, total_amount, status, supplier_id/code/name 快照
purchase_order_items     unit_price, amount, qty, received_qty（滚动维护）
purchase_receipts        po_id, receipt_no, warehouse_id, received_at
purchase_receipt_items   receipt_id, po_item_id, qty
purchase_receipt_exceptions
    exception_type ∈ WRONG_PRODUCT / UNIT_MISMATCH / SHORT_SHIPMENT
                     / DAMAGE / QUALITY_DISPUTE / RETURN
    qty, status ∈ OPEN / RESOLVED, resolution
```

**三单里的前两单已经完整。**

### 对开发计划的一处修正

计划写着「A4 依赖 A3(质检),不合格数量要进扣款,顺序反了要返工」。

**这条依赖可以放宽。** `purchase_receipt_exceptions` 已经能记短装、破损、质量争议、退货**及其数量**——
驱动扣款的那个数字现在就有。A3 会补上更完整的质检记录(检验结论、附件、处置方式),
但 A4 不必等它。

### 缺的

- 供应商发票(三单的第三条腿)
- 付款记录
- 核销(付款 ↔ 发票/订单 的多对多金额分配)
- 供应商付款条件(账期、定金比例)——`suppliers` 表目前只有 `currency`
- 采购订单状态机里没有任何付款相关状态

## 三、照抄应收侧,不另起一套

`services/export/internal/app/receipt.go`(527 行)已经把这套做对了,设计哲学写在注释里:

> **「对账是一场关于完整性的争论——在门口就过滤,以后永远解释不了银行余额和系统的差额」**
>
> **「流水是事实,核销是判断,而判断是会被修正的」**
>
> **「不是 DELETE 也不是 UPDATE。求和仍然给出今天的答案,按顺序读则给出某人如何得到这个答案的历史,包括那个错误」**

`receipt_allocations` 里三个必抄的细节:

```sql
amount      NUMERIC(18,2) NOT NULL CHECK (amount <> 0),  -- 冲销为负行
fee_amount  NUMERIC(18,2) NOT NULL DEFAULT 0,            -- 中间行扣费单独记
reversal_of BIGINT REFERENCES receipt_allocations(id),

-- 一行只能被冲销一次。没有它，点两次「冲销」余额会多加一倍。
CREATE UNIQUE INDEX receipt_alloc_reversal_once
    ON receipt_allocations (reversal_of) WHERE reversal_of IS NOT NULL;
```

服务层的形状同样照抄:

```
RecordTransaction   记录银行说了什么，不做判断
Allocate(tx, lines) 决定这笔钱付了哪些单
ReverseAllocation   写一条相反的，不删不改
MarkIrrelevant      逃生口——没有它队列会被无关流水堵死，然后整页被忽略
ContractReceipts    多对多的另一半：一个合同分期收
OpenReceivables     喂给核销选择器的未结清列表
```

## 四、银行流水放哪里（一个需要决定的架构问题）

`bank_transactions` 现在住在 **export 服务**。应付侧属于 **procurement**。跨服务共用一张表不行。

| | 做法 | 代价 |
|---|---|---|
| **A** | 把银行流水抽成共享的财务能力 | 干净、符合「一本流水」的会计原则,但要动已在跑的应收侧 |
| **B** | procurement 自建付款表 | 不动老代码,但银行余额要在两处分别对 |

### 建议:先走 B,但为 A 留好接口

理由是**应收和应付的问题形状不同**:

- **应收**是「一笔来路不明的钱到账了,它是谁付的?」——必须流水优先,因为你事先不知道
- **应付**是「我们主动电汇给工厂」——**付款的那一刻我们就知道付给谁、为哪张单**,
  「把未知的钱匹配到某个单据」这个难题基本不存在

所以 B 在应付侧损失很小。但「一本流水才能解释银行余额」这个原则是对的,
所以 `supplier_payments` **从第一天就带上 `bank_ref` 和 `bank_txn_id`(可空)**,
将来合并时不用改表。

**这是一笔明确记账的技术债,写在这里而不是留给以后考古。**

## 五、数据模型

### 5.1 `supplier_invoices` — 第三条腿

```sql
CREATE TABLE supplier_invoices (
    id              BIGSERIAL     PRIMARY KEY,
    tenant_id       BIGINT        NOT NULL DEFAULT 1,

    -- 供应商快照，理由同 purchase_orders：改名不能改写历史单据
    supplier_id     BIGINT        NOT NULL,
    supplier_code   VARCHAR(50)   NOT NULL DEFAULT '',
    supplier_name   VARCHAR(200)  NOT NULL DEFAULT '',

    -- 工厂给的发票号。同一供应商下唯一——重复录入是最常见的重复付款起点。
    invoice_no      VARCHAR(100)  NOT NULL,

    -- 外贸场景下这张纸可能是好几种东西，而它决定能不能退税
    invoice_type    VARCHAR(24)   NOT NULL DEFAULT 'COMMERCIAL'
        CHECK (invoice_type IN ('COMMERCIAL','PROFORMA','VAT_SPECIAL','VAT_PLAIN','OTHER')),

    currency        VARCHAR(8)    NOT NULL,
    -- 工厂说我们欠多少。这是对方的主张，不是我们的结论。
    total_amount    NUMERIC(18,2) NOT NULL CHECK (total_amount > 0),
    tax_amount      NUMERIC(18,2) NOT NULL DEFAULT 0,

    invoice_date    DATE          NOT NULL,
    -- 账期到期日。逾期未付的清单靠它。
    due_date        DATE,

    -- 三单匹配结论。抄 Odoo 的态度：不硬拦，只标状态。
    match_status    VARCHAR(16)   NOT NULL DEFAULT 'PENDING'
        CHECK (match_status IN ('PENDING','MATCHED','EXCEPTION')),
    match_note      TEXT          NOT NULL DEFAULT '',

    status          VARCHAR(16)   NOT NULL DEFAULT 'OPEN'
        CHECK (status IN ('OPEN','SETTLED','VOID')),
    void_reason     TEXT          NOT NULL DEFAULT '',

    attachment_key  VARCHAR(500)  NOT NULL DEFAULT '',  -- 发票扫描件
    created_by_id   BIGINT        NOT NULL DEFAULT 0,
    created_by_name VARCHAR(100)  NOT NULL DEFAULT '',
    created_at      TIMESTAMPTZ   NOT NULL DEFAULT now(),

    UNIQUE (tenant_id, supplier_id, invoice_no)
);
```

```sql
CREATE TABLE supplier_invoice_lines (
    id           BIGSERIAL     PRIMARY KEY,
    tenant_id    BIGINT        NOT NULL DEFAULT 1,
    invoice_id   BIGINT        NOT NULL REFERENCES supplier_invoices(id) ON DELETE CASCADE,
    -- 对上哪一条采购订单行。可空：工厂偶尔会开出订单上没有的费用（运费、打样费）。
    po_item_id   BIGINT        REFERENCES purchase_order_items(id),
    po_id        BIGINT        REFERENCES purchase_orders(id),
    description  VARCHAR(300)  NOT NULL DEFAULT '',
    qty          NUMERIC(18,4) NOT NULL DEFAULT 0,
    unit_price   NUMERIC(18,4) NOT NULL DEFAULT 0,
    amount       NUMERIC(18,2) NOT NULL
);
```

### 5.2 `supplier_payments` — 钱出去了

```sql
CREATE TABLE supplier_payments (
    id              BIGSERIAL     PRIMARY KEY,
    tenant_id       BIGINT        NOT NULL DEFAULT 1,
    supplier_id     BIGINT        NOT NULL,
    supplier_name   VARCHAR(200)  NOT NULL DEFAULT '',

    payment_no      VARCHAR(50)   NOT NULL,
    -- 付款的性质。ADVANCE 是定金——付出去时三单一单都没有。
    payment_type    VARCHAR(16)   NOT NULL DEFAULT 'SETTLEMENT'
        CHECK (payment_type IN ('ADVANCE','SETTLEMENT','REFUND')),

    currency        VARCHAR(8)    NOT NULL,
    amount          NUMERIC(18,2) NOT NULL CHECK (amount > 0),
    -- 本位币金额与所用汇率。外贸对账最容易做错的地方：
    -- 订单是 USD、付款是 CNY，中间的差额必须落到损益，不能默默吃掉。
    base_currency   VARCHAR(8)    NOT NULL DEFAULT 'CNY',
    base_amount     NUMERIC(18,2) NOT NULL DEFAULT 0,
    fx_rate         NUMERIC(18,8) NOT NULL DEFAULT 0,

    paid_at         DATE          NOT NULL,
    method          VARCHAR(24)   NOT NULL DEFAULT 'WIRE'
        CHECK (method IN ('WIRE','LC','TT','CASH','OTHER')),

    -- 为将来并回统一银行流水留的口子（见第四节）。现在可空。
    bank_ref        VARCHAR(100)  NOT NULL DEFAULT '',
    bank_txn_id     BIGINT,

    -- 未分配余额 = amount - Σ allocations。定金付出去后这里是满额挂着。
    -- 不存成列：由 allocations 求和得出，避免两份真相。

    remark          TEXT          NOT NULL DEFAULT '',
    created_by_id   BIGINT        NOT NULL DEFAULT 0,
    created_by_name VARCHAR(100)  NOT NULL DEFAULT '',
    created_at      TIMESTAMPTZ   NOT NULL DEFAULT now(),

    UNIQUE (tenant_id, payment_no)
);
```

### 5.3 `payment_allocations` — 核销

**这张表是整个方案的核心**,形状照抄 `receipt_allocations`,但有一处关键差别:
**核销目标可以是发票,也可以是采购订单。**

```sql
CREATE TABLE payment_allocations (
    id            BIGSERIAL     PRIMARY KEY,
    tenant_id     BIGINT        NOT NULL DEFAULT 1,
    payment_id    BIGINT        NOT NULL REFERENCES supplier_payments(id),

    -- 二选一，且必须恰好一个：
    --   invoice_id 非空 = 结算（付发票）
    --   po_id      非空 = 预付（付定金，此时还没有发票）
    invoice_id    BIGINT        REFERENCES supplier_invoices(id),
    po_id         BIGINT        REFERENCES purchase_orders(id),
    CHECK ((invoice_id IS NOT NULL) <> (po_id IS NOT NULL)),

    amount        NUMERIC(18,2) NOT NULL CHECK (amount <> 0),  -- 冲销为负
    -- 中间行扣费：我们汇出 50,000，工厂收到 49,975，而合同照样按 50,000 结清。
    fee_amount    NUMERIC(18,2) NOT NULL DEFAULT 0,
    currency      VARCHAR(8)    NOT NULL,

    reversal_of   BIGINT        REFERENCES payment_allocations(id),
    reverse_reason TEXT         NOT NULL DEFAULT '',

    allocated_by  BIGINT        NOT NULL DEFAULT 0,
    allocated_by_name VARCHAR(100) NOT NULL DEFAULT '',
    allocated_at  TIMESTAMPTZ   NOT NULL DEFAULT now()
);

CREATE INDEX payment_alloc_payment_idx ON payment_allocations (tenant_id, payment_id);
CREATE INDEX payment_alloc_invoice_idx ON payment_allocations (tenant_id, invoice_id);
CREATE INDEX payment_alloc_po_idx      ON payment_allocations (tenant_id, po_id);

-- 同 receipt_allocations：一行只能被冲销一次。
CREATE UNIQUE INDEX payment_alloc_reversal_once
    ON payment_allocations (reversal_of) WHERE reversal_of IS NOT NULL;
```

### 5.4 预付款怎么走完全程

定金是这套模型里唯一不走「三单」的路径,单独说清楚:

```
1. 下采购订单 100,000 USD                    purchase_orders
2. 付 30% 定金 30,000                        supplier_payments (type=ADVANCE)
3. 核销到订单，不是发票                       payment_allocations (po_id=…, amount=30000)
        ↑ 此时它在会计上是「预付账款」，一项资产，不是费用
4. 工厂发货、我们收货                         purchase_receipts
5. 工厂开来发票 100,000                       supplier_invoices
6. 把第 3 步的预付「转」到发票上               冲销 po 那条 + 新增 invoice 那条
7. 付尾款 70,000                             supplier_payments (type=SETTLEMENT)
8. 核销到发票                                 payment_allocations (invoice_id=…)
9. 发票已结清                                 status=SETTLED
```

第 6 步是**两条 allocation**(一条负的冲掉订单预付、一条正的挂到发票),
而不是 UPDATE 一行——这样「这笔定金后来去哪了」在表里读得出来。

## 六、三单匹配怎么算

对发票的每一行:

```
应付数量 = 该 po_item 的已收数量
         − Σ 该 po_item 未解决的异常数量（SHORT_SHIPMENT / DAMAGE
                                        / QUALITY_DISPUTE / RETURN）
应付金额 = 应付数量 × 采购订单单价      ← 用我们的价，不用发票的价
差额     = 发票行金额 − 应付金额
```

| 情况 | 结论 |
|---|---|
| 全部行 \|差额\| ≤ 容差 | `MATCHED` |
| 任一行超出容差 | `EXCEPTION`,`match_note` 写明哪一行、差多少、为什么 |
| 有行匹配不到 po_item | `EXCEPTION`(工厂加收了订单外的费用) |

**容差可配置**(百分比 + 绝对值取小者),照 ERPNext 的做法。

### 不硬拦

抄 Odoo:`EXCEPTION` **不阻止**录入、不阻止付款,只是在界面上标出来、
在待办里排前面。理由和邮件追踪那件事是同一条:

> **给一个诚实的状态,而不是一个假装确定的判断,也不是粗暴地拦住人。**

「工厂多开了 2%,因为运费涨了」这种事采购员天天遇到。系统该记下差异让人决策,
而不是不让他往下走。

## 七、对账视图（这才是用户要的东西）

按供应商一行:

| 列 | 来源 |
|---|---|
| 订单金额 | Σ `purchase_orders.total_amount`(未取消) |
| 已收金额 | Σ `received_qty × unit_price` |
| 异常扣减 | Σ 未解决异常数量 × 单价 |
| 已开票 | Σ `supplier_invoices.total_amount`(未作废) |
| 已付款 | Σ `payment_allocations.amount`(含负行) |
| 预付未冲抵 | Σ 挂在 po 上的 allocation |
| **未付余额** | 已开票 − 已付款 |
| 逾期 | `due_date < today` 且未结清 |

点进去是这个供应商的明细:订单、收货、异常、发票、付款、核销,按时间排。

## 八、分期实施

| 阶段 | 内容 | 工作量 |
|---|---|---|
| **P1** | `supplier_invoices` + `supplier_invoice_lines`,录入 / 上传扫描件 / 列表 | 小 |
| **P2** | 三单匹配计算 + `match_status` + 差异说明 | 中 |
| **P3** | `supplier_payments` + `payment_allocations` + 核销界面(含冲销) | 中 |
| **P4** | 预付款:核销到 PO、转挂到发票 | 小(建在 P3 之上) |
| **P5** | 对账视图 + 逾期清单 | 小 |
| **P6** | 多币种:汇率快照、汇兑损益(接 `services/fx`) | 中 |

**P1→P5 每一阶段都可单独上线并产生价值**,P6 可以推迟到有非本位币付款时。
