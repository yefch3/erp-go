### A5 ✅ 货没到齐也能关单，差额回到待采购（2026-08-23 完成）

**场景**：订了 100 吨，工厂只能给 80 吨，也确实只发了 80 吨。在此之前
这单永远关不掉——关单要求「全部收满」，而那 20 吨永远不会来。货收完了、
钱付了、事情办完了，系统却一直在等，财务和采购只能在系统外记一笔。

**业务定的做法**：关掉这单的时候，把没到的 20 吨放回待采购清单，人点一下
确认，然后另找一家工厂开新单。

**实现**：关单时如果货没到齐，必须回答两件事——剩下的另找工厂买还是不要
了、以及为什么。选「另找工厂」就把差额退回待采购（用的是取消订单时那套
现成的 `ReleaseRequirementOrdered`），需求状态回到「部分已订」，新单能照常
从池子里领走它。

**订单明细的数量一个字不改**：「订了 100」是事实，「认 80 就算完」是判断
——同 A4「付款是事实、核销是判断」、A3「收货是事实、结不结案是判断」。

两道闸仍然在：悬着的到货异常和质检照样拦着不让关。

> 一个需求本来就支持多张采购单（`open_qty = 要的 − 已下单的`），所以差额
> 一旦回到池子，「80 吨找甲厂、20 吨找乙厂」就是现成的路。缺的一直只是
> 「把没到的部分放回去」这一步。

#### A5 续：一开始就知道只供 80 吨（2026-08-23 完成）

上面写的是「订了 100，到货只有 80」。业务真正常遇到的是另一件事：**询价
比价的时候就知道这家只能供 80 吨**。这时该做的不是等货不齐再关单，而是
直接按 80 吨下单，剩下 20 吨另找一家或过些天向同一家补。

把四条路挨个在系统里跑了一遍（`TestA5Probe`，一次性探针），结果：

| 操作 | 当时 | 现在 |
|---|---|---|
| 一开始就只订 80 | 能 | 能 |
| 剩下 20 吨另找一家（合同来源的需求） | 能 | 能 |
| 作废还没到货的采购单，重新采购 | 能 | 能 |
| 剩下 20 吨另找一家（**客户报价来源**） | 挡住 | **写原因放行** |
| 剩下 20 吨还找同一家补购（**客户报价来源**） | 挡住 | **写原因放行** |
| 已经到了一部分的单再作废 | 挡住 | 仍然挡住（见下） |

**为什么原来挡住**：这条线上供应商和数量是询价比价定死、报给客户、再签
合同的，所以系统要求采购单的供应商必须等于成本方案里那家（换一家，报价
时算的利润就变了），另有一条唯一索引拦重复点击下单，顺带把正当的补购也
拦了。顾虑对，做法太硬。

**改法**：照这里现成的规矩办——偏离已确认方案，**写明原因就放行，原因随
单存档**（`source_change_reason`，和「改了确认报价的单价或币种要写原因」
同一个字段）。前端默认仍然锁着供应商下拉框（这是常态），要换得先点一下
「改向其他供应商」，是一次明确动作而不是随手改。

**防重复点击没有丢**：真正的把关本来就在别处——下单事务开头把需求整行锁
住，且不允许超过「还能下多少」。唯一索引降级成普通索引，判断挪到应用层
并分成两种：**还停在草稿的**仍然当重复处理（前端认这个错误码，会把上一张
调出来接着办），**已经确认下单的**才是补购，写原因放行。

**顺带补一个洞**：「待采购并审批」页原来只列「一点没买」的需求，下了第一
张单整批就从眼前消失了——剩下的 20 吨得靠人记着。改成把「部分已订」的一
并列出，买齐了才消失。

**「已经到货了还能不能作废」没有放开**：50 吨已经在码头库里，作废会让这
批货不属于任何订单、开不了票也付不了款。系统原来提示「请走退货流程」，
但退货流程其实只有一条记异常的记录、不会退数量——这句提示是空头支票。
这种情况应该走关单那条路：认下已到的 50 吨、照常开票付款，剩下的放回待
采购另找工厂。**待业务确认**是否确实有「货到了但整单要推翻」的场景。

### C6 ⬜ 智能路由：让用户按活儿挑模型

**核验结论（2026-08-24）：地基已经有一半，另一半是个陷阱。**

已经有的：

- `mail_excel_jobs.model` —— **每次转换用了哪个模型早就落库了**（`00035_excel_jobs.sql`
  第 16 行就有这一列），不用新建字段
- 转换结果一路带着 `Model` 出来，worker 存的时候顺手就写了

缺的两样：

- **模型是一个进程一个**：`OPENAI_MODEL` 从环境变量读（`config.go:119`，默认
  `gpt-5.6-luna`），全公司、所有人、所有转换都是它。要换只能改配置重启
- **单价也只有一份**：`ModelPricing` 是一个结构体、一对数
  （`excel_usage.go:23`），`ExcelUsageByMonth` 按「月 + 人」分组，**不按模型分**

#### 先说那个陷阱

单价是一份，路由是多模型。**这两件事一起上线，钱就算错了**——用 Sol 跑的那次
会被按 Luna 的价算。而 5.6 家族最贵和最便宜差 **20 倍**（Sol $4/$20 对
Luna $0.20/$1.20），错一次就错一个数量级。

**所以顺序是死的：先做按模型分价，再放开选择。** 反过来做，用量页会给出一个
看着像账、其实是错的数字——**比没有数字更坏**，因为没人会去怀疑它。这和
「空 ≠ 0」是同一条：算不出来就该说算不出来，不能给个像模像样的错数。

#### 三步，顺序不能换

| 步 | 做什么 | 为什么卡在这个位置 |
|---|---|---|
| 一 | **单价按模型配**：`ModelPricing` 从一份变成一张表（模型 → 输入价/输出价）；`ExcelUsageByMonth` 的分组加上 `model`；用量页按模型分行 | 没有这一步，后面两步都在算错钱 |
| 二 | **可选清单**：管理员配「本租户允许哪几个模型」，各自的价和一句人话说明。**不给自由填**——填错一个型号名就是一次失败的转换加一次白花的钱 | 先收口，再放开 |
| 三 | **转换时选**：生成 Excel 的入口给个下拉，默认走清单里的默认项 | 前两步做完这步很小 |

#### 限量必须同时上

### D2 ✅ 合同执行进程一览表（2026-08-23 完成）

**为什么要它**：「这单到哪了」原来没有一个人答得上来。合同金额在出口合同
页，订没订货在采购页，货走没走在出运页，钱收没收在银行流水页——四个页面、
四个部门，谁都只看得见自己那一段。

**一行一合同，四段进程**：

| 段 | 口径 | 为什么这么定 |
|---|---|---|
| 采购 | **按项数**：共 N 项 / 订齐 M 项 / 到齐 K 项 | 一张合同上 100 吨钢卷和 50 件配件加不起来；折成金额又会把采购成本混进一张讲营收的表 |
| 出运 | **按金额**：已出运额 ÷ 合同额 | 和收款同一把尺，两个数直接可比——走了六成货、收了三成款，钱货脱节一眼看得出 |
| 船期 | **最新一班**的状态 + 班次数 | 问的是当下；历史班次点进船期页看 |
| 收款 | **按金额** + 逾期天数（复用 E1 的到期日） | 同上 |

**取数的形状**：出口那边三条腿（合同 / 已出运 / 已收款）在同一个库里，一条
SQL 出完，分页和数据范围都由它定；采购和船期在别的服务，按**这一页的合同**
批量问回来拼上——**一页两次调用，不是一行两次**。20 行也是两次。

**折算的三条讲究**（都在测试里钉住了）：按产品配对而不是按明细行（改版会
重写行 id，按行配对会让改版前发出去的货凭空消失）；单价取生效版本的**加权
均价**（同一产品偶尔落在两行上）；**超发不夹紧**——改版把量调小而货已经发
了，13000 > 合同的 10000 要露出来，不是抹平。

**围栏只设一道**：合同能不能看，由出口那道现成的围栏判；采购和船期两列
**不再单独设栏**。这是刻意的——同一行里有的列有数、有的列空着，读起来就是
「没采购」，而真相是「你没权限看」。**一个会给出错误答案的表格比没有这张
表格更糟。** 安全性靠另一头保证：这一行只给进度数字，不给供应商、不给采购
价；要看细节得点进去，那时各模块自己的围栏照常生效。

**一条腿断了不装作是零**：采购或船期取不回来时，那一列写「取不到」并打灰，
顶上横幅说明「不是『没有』，是『没问到』」。零在这张表上的意思是「还没开始
采购」，和「服务连不上」是完全不同的两件事，读的人会照着做出完全不同的决定。
顶部那个「货还没订齐」的合计也一并让位——浏览器实测时正是它先露的马脚：
停掉采购服务后数字从 2 跳到 4，那 4 是个吓人的假数。

### D1 ⬜ 出口退税：流程与实现思路（尚未动工，仍有问题待业务确认）

**业务给的流程（2026-08-23）**：

1. **退（免）税备案先做** —— 企业级的一次性动作，没备案后面全都白搭
2. **海关下报关单** —— 出口报关后拿到报关单，这是退税的起算凭证
3. **准备对应的进项发票** —— 买货时供应商开的增值税专用发票，退的就是这笔进项税
4. **其余单据备齐** —— 出口合同、运单、报关委托协议等
5. **第一次会比较麻烦** —— 首次申报的资料多、口径生，之后是重复劳动

**这句流程改变了实现方向**：退税模块的核心**不是算税**（税率查表、金额乘除，Excel 都能做），
而是**「一批出口的单据到底齐没齐」**。真正的痛点是：一票出口要凑齐报关单 + 进项发票 +
合同 + 运单 + 委托协议，缺一样就申报不了；笔数一多，人靠脑子记哪票缺哪张。所以这个模块
本质是**按出口批次归集单据的清单 + 缺件提醒**——和 A3 质检、A4 三单核对是同一种东西：
**把「齐不齐」变成系统能回答的问题**。

**初步设计（待需求会确认）**：

- **退税批次**：一票出口（或一张报关单）为一个批次，关联合同、出运单、采购订单
- **单据清单**：每个批次一张固定的必备单据表（报关单/进项发票/合同/运单/委托协议/……），
  每项有「已上传 / 缺失 / 不适用」三态，附件走已有的 S3 通道
- **进项发票配对**：出口的货是从哪几张采购单来的 → 那几张供应商发票就是进项来源。
  三单核对已经把这条链打通了，退税只是换个角度读它
- **状态流**：备案 → 收单 → 齐套 → 申报 → 已退。齐套之前不许申报（同 A3 的闸门思路）
- **台账与提醒**：申报期限倒计时；久未齐套的批次上工作台

**要问业务的**：退税率从哪来（商品编码对应，还是人工填）、申报周期与期限、
退税额怎么核对到账、单证不齐时的常见处置。

### E1 ✅ 应收账款到期提醒（2026-08-23 完成）——细节

**到期日从哪来**：业务已定——**账期从合同生效日起算**（收到定金/预付款/
信用证之后才去下采购单，所以合同生效本身就意味着首付到位，之后的 120/150
天算的是尾款）。`due_date = 合同生效日 + 客户 payment_days`，**在签署那一刻
算好落库**，不是每次现算：客户改账期不该动已经发生的账——今天把账期从 120
调到 90，半年前那批合同不该「突然逾期」。

**第一期已完成（2026-08-23）**：`contracts.receivable_due_date` 落库（签署
事务内写，只写一次）、客户没配账期时**留空而不是当天到期**、催收清单页
（逾期红行 + 还剩几天 + 三个指标 + 逾期/未配账期两个筛子）、按销售负责人
围栏、存量补算 `BackfillReceivableDue`。集成测试九项判断全钉住，顺带把
`EXPORT_TEST_DSN` 接进 CI——export 此前一个 DB 测试都没跑过。

**第二期已完成（同日）**：`receivable_reminders` + 每日 worker + 站内信铃铛。
四档时机（30 天内 SOON / 7 天内 DUE / 逾期按周 OVERDUE）**用范围而非等号
判断**——写成「今天正好是到期前 30 天」的话，worker 那天没跑就永远错过；
范围加唯一键则是停几天再起来能一次补齐且不重复。跨租户扫描，新租户不需
要额外配置。铃铛按人隔离，逾期红点/临期橙点/其余灰点。

**顺带修的**：超管的数据范围一直是空的（引导只授权限、没配范围，而
export 的种子迁移跑在引导之前），管理员打开合同/收款/应收全是空的而
权限页正常——bootstrap 补上 + 迁移 00043 订正已有租户 + 测试钉住。
`mail` 有意不给：让超管看别人的邮箱该是显式决定。

**提醒怎么发**：复用船期那套现成的 worker（定时轮询 + 幂等 + 通知 + 工作台），
不新建一套。默认到期前 30/7/0 天各提醒一次，逾期后每 7 天一次。

**为什么它排第一**：这是三个里唯一**直接对应真金白银**的——逾期应收收不回来是
坏账，而现在系统能算出欠款却答不出「什么时候该收」。而且它是 E3 的前提：
没有逾期数据，信用评级只能拍脑袋。

### E2 ✅ 提单签发提醒（2026-08-23 完成）

`shipping_bl_reminders` + 每日 worker + 船形铃铛。触发：船开了（`atd`，
没登记则退回 `etd`）、满 3 天、且没有有效的 `BILL_OF_LADING_FINAL`——
**草稿不算**，草稿不是能拿去交单的东西。之后每 3 天一轮，直到正本上传。

**收件人是一群人，但表里一人一行**：部门是收件人的来源，不是收件人本身。
展开成多行之后「谁读了、谁还没读」才是可回答的问题；发一条挂在部门名下，

没有复用 `shipping_arrival_reminders`：那张表和「到港」绑得很紧（外键指向
目的港节点、worker 里 JOIN 出到港文案、状态机为发邮件而设）。改用 E1 刚
验证过的模式——一条 SQL 扫描 + `INSERT ON CONFLICT`，幂等交给唯一键。

### E3 ✅ 信用评级第一期（2026-08-23 完成）

**别做成死字段**。人工填一个 A/B/C/D 下拉最省事，但会变成「填了没人更新」。
有用的做法是**系统给建议、人工定级**：系统算出「平均逾期 23 天、最大欠款 12 万美元、
近一年 8 笔全部按时」，评级人看着数据打分，评级连同依据一起存历史。

**第一期做的是人工那一半**（原计划就是这么分的）：

- **评级本身**：A/B/C/D，客户和供应商各一套，共用一张 `credit_ratings` 表——
  问的问题不同，但「谁在什么时候依据什么评了什么」是同一个形状
- **依据必填**。说不出为什么的评级等于没评，这是整张表存在的理由
- **每改一次留一行**，上一档记在同一行里——「从 A 降到 C」要一眼看得出，
  页面上降级用红点标出来
- **「多久没评了」**摆在评级旁边。一个三年没动过的 A，看着和上周刚判的 A
  一模一样，而它们说的完全不是一回事。超过半年自己变黄
- **依据数字留了位置**（`evidence` JSONB）。现在大多是空的，页面上明说
  「暂无数据」而不是显示 0——一个凭空的 0 看着像结论

**客户看什么**：逾期笔数、最长逾期、当前欠款。
**供应商看什么**（业务定的）：交期准不准、供货足不足量、质量合格率——
都是「看货」的维度，不含报价响应速度。三者在系统里都有现成的数据模型
（采购单的要求到货日、A5 的差额记录、A3 的质检记录），只是还没有数据。

**没做的**：系统给建议。生产上合同 0 张、采购单 0 条，算出来只会是一排 0。
等数据攒起来，往 `evidence` 里填就是，页面和历史都不用改。

> 踩到过一次：`credit_grade` 最初用 `CHAR(1)`，PostgreSQL 会把空串补成一个
> 空格，于是「没评过」读出来是一个看不见的空格——判空失败，按钮写着「重新
> 评级」而那家客户一次都没评过。改成 `VARCHAR(1)`。

### E4 ⬜ 货轮到港自动追踪

**核验结论：数据模型已经完备，缺的只是数据源。** `shipping_route_nodes`
支持整条航线——起运港 / 中转港 / **临时挂靠** / 目的港，每个节点都有
**原始 ETA**、**最新 ETA**、实际到港、原始 ETD、最新 ETD、实际离港，
节点状态走 计划 → 临近 → 已到 → 已离（可标记跳过）。主表有
ETD/ATD/ETA/ATA 与七种状态，另有 `shipping_delay_events` 延误记录、
可配规则的到港提醒、以及完整的变更留痕。

`original_eta_at` 与 `latest_eta_at` **分开存**这个设计本身就说明问题：
它天生是为「船公司改了 ETA、要看出改了多少」准备的。地基是按自动追踪
的样子打的，只是没接上源。

**但更新全是人工**：`UpdateRouteNodeTimes` / `SetDestinationETA` 都带
`updated_by`——船务的人从船司网站或邮件查到最新 ETA 再手填。搜遍
shipping 服务，**没有一行承运人 API、AIS 或第三方追踪的代码**。

| | 方案 | 成本 | 拿到什么 | 前提 |
|---|---|---|---|---|
| **甲** | **解析船公司邮件通知**（推荐先做）。船司本来就发 ETA 变更、到港、可提货通知到我们邮箱，而邮件系统 + AI 提取（C 组）已经在跑 | **零外部费用**，只有模型调用的几分钱 | 提单号 + 新 ETA → 自动更新 `latest_eta_at`，**人确认后生效**（照 C 组「AI 出草稿，人确认」）。到港通知还能顺带触发 ATA 与 E2 的提单提醒 | 无 |
| 乙 | **第三方集装箱追踪 API**（Terminal49 / Vizion / Portcast 这类），一个接口覆盖所有船司 | 业内按柜计费或订阅制，**量级需询价**——月柜量决定值不值 | 船司系统里的真实事件：装船 / 离港 / 转船 / 到港 / 卸货 / 可提货，最准最结构化 | **系统现在没有集装箱号字段**，要先补 |
| 丙 | **AIS 船舶位置**（MarineTraffic 等） | 最低（几百美元/年档） | 只有船的经纬度 | 无 |

**丙基本可以排除**：它追的是**船**不是**你的货**。船到港 ≠ 你的柜卸下来了
≠ 你能提货。适合大屏可视化，不适合驱动业务。

**建议先做甲**：零外部成本、复用已有的邮件 + AI 地基、覆盖面最广，
解决的正是现在最费人的那段（船务盯着邮箱手改 ETA）。做完若发现邮件
不够及时或不够全，再上乙。

**待业务确认**：① 主要用哪几家船公司（集中在两三家的话甲的邮件格式好
收敛）；② 一个月多少个柜（决定乙值不值）；③ 真正想知道的是「船到哪了」、
「什么时候到港」还是「我的柜什么时候能提货」——第三个业务价值最高，
但也最依赖乙。

**工作量**：甲中 · **依赖**：甲无（C 组的提取件可复用）；乙需先补集装箱号
· **来源**：2026-08-23 业务提问后核验

### E5 ⬜ 单点登录（SSO）

**核验结论（2026-08-24）：接进来的口子很干净，难的不是登录本身。**

已经有的：

- 登录成功后发的是一张 JWT（`pkg/authtoken` 的 `Issue`，带租户、员工号、
  姓名、邮箱）。**SSO 要替换的只是「怎么证明是本人」这一步，证完照样发同
  一张票** —— 网关和所有服务一行都不用动。这是最好的消息：接入点是一个
  函数，不是一层。
- OAuth 那套跳转-回调-验票的流程**我们写过一次**
  （`services/mail/internal/app/oauth.go`，连 Gmail 邮箱用的）。不是新领域。
- 已经有邀请/激活流程（`email_verified_at`）和租户域名校验
  （`IsTenantDomain`）。

缺的：

- `employees` 表**没有任何外部身份字段**，没地方记「这个人是企业微信里的谁」。
- 现在靠邮箱定位账号（`GetUserByEmail`），邮箱就是身份。

#### 值钱的是第二条，不是第一条

1. 少记一个密码 —— 300 人推广时阻力小很多。
2. **离职能一键关掉** —— 今天有人离职，要有人**记得**去 ERP 里停用他；忘了，
   账号就一直活着。接了 SSO，身份中心里一停，所有系统同时进不去。这是安全
   上的实质改善，不是便利性。
3. 我们不再保管密码，少一处可泄露的东西。

#### 先问一句：ERP 是不是员工唯一要登的系统

是的话，**这件事先别做**。

「不用再记密码」这个好处**不是 SSO 本身给的**，是因为员工本来就登着企业微信
或飞书——他在那边已经证明过身份了，我们只是去问一句。换成自建一个身份中心，
他没登着，照样要输密码：密码数量没变，还多了一次跳转和一个要运维的服务。

自建身份中心（Keycloak、Authentik、Apereo CAS 这类）划算的前提是**有好几个
系统**：ERP、网站后台、内部工具、报表……一处认证处处通，才值回运维成本。
只有一个系统时，自建等于把现在的登录搬个家。

| 员工还登什么 | 该做什么 |
|---|---|
| 只有 ERP | **先别做**。现在的邮箱 + 密码没问题，力气花在别处 |
| 公司在用企业微信/飞书，且天天开着 | 接它。零新密码，而且离职一键关 |
| 有好几个自建系统 | 这时自建身份中心才开始划算 |

顺带澄清一个容易混的说法：**CAS 是一个协议，不是一家第三方公司**（耶鲁做的，
开源实现叫 Apereo CAS，国内多见于学校的统一认证）。企业场景现在的主流是
OIDC，不是 CAS。所以不存在「必须去某个第三方 CAS 认证」这回事。

而**对接代码本来就是我们自己写**，没有任何规矩要求用第三方 SDK。真正不该自己
发明的只有一样：协议和密码学。照着 OIDC 规范写客户端是查文档干活；自己设计
一套「票怎么签、怎么验、怎么过期」是在没有同行评审的情况下做安全设计。这条
我们其实已经站对了——现在发的 JWT 用的是标准库和标准算法，没自创东西。

#### 三个必须先定的问题

| 问题 | 为什么卡人 |
|---|---|
| **接哪家** | 企业微信 / 飞书 / 钉钉 / Microsoft 365。取决于公司本来在用哪个 —— 员工没登着的那家，SSO 等于多一道手续，不是少一道 |
| **怎么对上员工** | 按邮箱对最自然，但**身份中心里的邮箱和 ERP 里的可能不是同一个**。对不上的人会被挡在门外，而且往往是在他最急的时候 |
| **第一次登录** | 身份中心有、ERP 里没有的人：自动建账号还是拒绝？自动建就绕过了现在的邀请流程和 `IsTenantDomain` 校验 |

#### 本地后门是必须的，不是可选的

身份中心挂了，全公司进不去 ERP。所以必须保留**至少一个本地密码账号**：

- 它不走 SSO
- 现有的账号锁定与网关限流对它照旧有效 —— 那套东西不能因为接了 SSO 就拆
- 平时不用，但要定期确认它还登得进去。**没验证过的后门等于没有后门**

#### 不做双因子的话，SSO 反而更安全

现在 ERP 没有双因子（搜遍 iam 服务，TOTP/短信一个都没有）。接了 SSO 之后，
双因子由身份中心提供 —— 企业微信、飞书都有。**这是接 SSO 顺带拿到的东西**，
比我们自己实现一套划算得多。

**工作量**：中 · **依赖**：先定接哪家（业务决定，不是技术决定）
· **来源**：2026-08-24 讨论邮箱登录方式时提出

### E6 ⬜ 邮件规模化路线——人多起来之后，先坏哪、怎么修

> 2026-08-25 立项。起因：#216 让邮件后台服务任意多家公司之后，业务问「都轮询
> 会不会负担很大」。答案是负担本身还早，但**排队的形状**已经能看清了。这一节
> 把「先坏哪」按疼的顺序钉下来，连同当天算的容量数字，作为将来重估的基准——
> 同 MONITORING.md 记「配置当天真实水位」的道理。

#### 容量基准（2026-08-25 算的，依据代码注释里的实测值）

一个健康空邮箱过一遍 ≈ 0.2 秒；全局并发 8；轮询间隔 120 秒。

| 规模 | 每轮耗时 | 占用率 |
|---|---|---|
| 现在（1 家，约 3 个邮箱） | 0.1 秒 | ≈0% |
| 1 家 × 300 人 | 7.5 秒 | 6% |
| 5 家 × 300 人 | 37.5 秒 | 31% |
| **16 家 × 300 人 = 4,800 邮箱** | 120 秒 | **100%，轮询的天花板** |

#### 先坏哪（按用户先感受到的顺序）

1. **交互和后台抢同一个队**——「立即收信」和后台轮询共用同一个 8 槽的
   fleet，**没有优先级**。有人等的请求排在没人等的活后面；人多时点一下
   要等几秒起。已有的缓解：后台恰好在收你的邮箱时，点击直接共享它的结果
   （syncfleet 的 share-not-queue）；但不在当前批次里就得排。
   **这正是「大规模在线时更新排队慢」的根源。**
2. **一家一家顺序过**——A 公司 2,000 个邮箱过完才轮到 B 公司的 5 个。小客户
   觉得慢，原因在别的客户身上。现在无害，公司多了第一个被抱怨。
3. **服务商的墙**——IDLE 是每邮箱一条常开连接。几千条从一个 IP 出去，Gmail
   会限流。这是别人的墙，加机器没用。
4. **单进程假设（真正的硬天花板）**——fleet、健康退避表、IDLE 看守全在一个
   进程的内存里。开第二个 mail 实例 = 每个邮箱被收两遍、UID 高水位互相打架。
   **只能纵向扩，不能横向扩。**
5. **健康退避表重启即忘**——坏邮箱的「越退越慢」在内存里，每次部署后全部
   重来，重启瞬间所有坏邮箱一起撞一次。

#### 解法阶梯（每一步都有先例，按序做，不跳级）

| 步 | 做什么 | 先例 / 依据 | 什么时候做 |
|---|---|---|---|
| 一 | **fleet 分车道**：后台最多 6 槽，永远留 2 槽给点按钮的人 | ERPNext 的 short/long 双队列——快活不排慢活后面 | 用户开始抱怨「立即收信」慢时；改动小 |
| 二 | **Gmail 邮箱改走 Gmail API 推送**（watch + Pub/Sub）：变化 1-10 秒推达，常开连接和轮询整个卸掉 | Gmail 官方推荐；它自己都不用长连接模型——几十亿邮箱汇进一条耐久队列 | Gmail 邮箱到几百个时。**注意 watch 七天过期要每天续，忘了就静默漏信**——又是那类安静的坏 |
| 三 | **同步改队列 + 多实例 + 租约**：谁持有某邮箱的租约谁收 | Frappe 的 worker 池；任何要横向扩的任务系统 | 邮箱逼近几千、或单机真扛不住时。大改，没到量级别碰 |

263 这类只有 IMAP 的留在轮询池里——它们才是天花板 4,800 里的少数。

#### 明确不做的：按「在线状态」决定收不收

业界的在线检测是心跳 + 自动过期（Redis TTL），技术成熟。但拿来决定收信有两个
否决理由：**邮件不等人上线**——凌晨两点的西班牙客户询价会在系统里消失七小时，
谁都搜不到、没法被接手，而西语客户正是主要客群；以及**成本反了**——有团队用
这套做在线检测，最后为了够实时改成了每用户一条 WebSocket 长连接，等于为了省
一个常驻系统建了另一个常驻系统。轮询降频版（活跃的勤、不活跃的稀）保留在
工具箱里，但排在上面三步之后，且要等真实数字定「稀」是多稀。

**工作量**：步一小 · 步二中 · 步三大 · **依赖**：步二只覆盖 Gmail
· **来源**：2026-08-25 业务问负担时核验

## 二点八、底座修缮（F 组）——2026-08-25 多公司排查后立项

### F1 ✅ 事件认领写进处理事务——关掉硬杀丢事件的最后一个窗口（2026-08-25 完成）

> 背景：事件消费原来「失败一次就永久丢失」（PR #226 修复），修复后的语义是
> 先认领、再处理、失败就归还认领并重试，重试尽仍失败就停进死信表等人重放。

**还剩一个窗口**：认领已记、处理事务还没提交，这期间进程被**硬杀**（OOM、
kill -9、机器宕机），事件就丢了——重投会因为认领在而跳过一件从没干完的活。
窗口长度是整个处理时长（含重试退避，量级为秒）。要点：优雅停机是安全的
（收到停机信号会归还认领）；handler 提交之后崩溃也是安全的（跳过的是真正
干完的活）。只有硬杀在干活中间这一种情形会丢。

**做法**：kafkax 把一个「认领函数」传给 handler，handler 一路传到服务方法，
由它在**自己已有的那个事务里**调用一次（一行）。认领和业务写入同生共死：

| 被杀的时刻 | 结果 |
|---|---|
| 事务提交前 | 认领随事务回滚，重投时从头再来（不丢） |
| 事务提交后 | 认领在，重投时跳过真正干完的活（不重） |
| 偏移量提交失败 | 同上，重投时跳过（不重） |

**落地的样子**：9 个服务方法各加一个参数、事务里各加一行。签名类型是各服务
app 包自己的 `EventClaim`（裸函数），业务层不因此依赖 kafkax——这个包不该
知道事件是从 Kafka 来的。事前核实过：这 9 个方法**只**被事件消费者调用，
没有任何 HTTP 请求路径用它们，所以改签名不波及请求侧。

**顺带改掉的一处**：procurement 的 `ApplyConfirmationApproval` 原来是一条
裸 `pool.Exec`，没有事务。为了让认领和它同生共死，包进了事务。

**验红**：把认领挪回事务外（旧做法），核心测试当场报「这笔活最终该干成一次，
实际 0 次」——正是硬杀丢事件的样子。

### F2 🔶 银行流水收口——一份对账单，进账对合同、出账对付款单

**2026-08-26 立项。触发点是一次问「这三个页面怎么操作」，顺着查出来的。**

#### 现在是什么样

`bank_transactions` 这张表**存在两份**，在两个不同的数据库里：

| 谁的库 | 建于 | 怎么进去的 | 能对到什么 | 独有的字段 |
|---|---|---|---|---|
| 出口 | `export/00010_receipts.sql` | 只能**手工登记** | 出口合同（应收） | 收款账户、**汇款附言**、归类（与应收无关的六种） |
| 采购 | `procurement/00018_bank_transactions.sql` | 只能**导入 CSV** | 供应商付款单（应付） | 导入的文件名、导入人 |

采购那张表的建表注释里已经写明了这件事：

> 进账：钱到账了——**导进来只是为了完整，目前不匹配任何东西**；客户收款在
> 出口那本账里。

于是有两件事今天做不到：

1. **导进来的进账没法对合同**——它落在采购的库里，那本账不认识出口合同
2. **手工登记的出账没法对付款单**——它落在出口的库里，那本账不认识付款单

还有一处更实在的错：**供应商退款**（`supplier_payments.payment_type='REFUND'`，
供应商把钱退回来）是一笔**进账**，但它必须对到采购的付款单上。现在银行流水页
第 76 行写死了只有出账才给匹配按钮，所以这类钱永远对不上——**凡是退过款的
供应商，供应商对账那一行的欠款余额都是多算的。**

#### 为什么不是「按方向拆成两张表」

最直觉的分法是「进账归出口、出账归采购」。这条走不通，原因就是上面那个：

- 供应商退款 = 钱**进**来，归**供应商**
- 退款给客户 = 钱**出**去，归**客户**

**方向决定不了归属。** 归属必须是一个独立的字段。

#### 也不新开服务

一开始想过照 `fx` 的样子新开一个 bank 服务（银行流水确实是「谁都要用、谁都
不拥有」的事实）。但代价是新库、新接口、迁两张表、多一个要看的进程，买到的
只有一个名字对得上。

**用采购现有的那张表**——它已经有 CSV 导入、按流水号去重、双向存储、匹配与
取消匹配、以及一个能用的页面。出口那边需要的行由**网关**去拿再拼给页面，
出口服务本身不新增对采购的依赖。网关已经在干这种事（平台页的死信台账就是把
三个服务的数据汇成一张表）。

#### 要做的四件事

**一、✅ 给 `bank_transactions` 加「归属」字段**（2026-08-26 完成，见本节末），取值是一个五选一（含空）：

| 归属 | 含义 | 接着做什么 |
|---|---|---|
| 空 | **待处理**。默认值 | 列表默认筛这一档 |
| `CUSTOMER` | 客户收款 | 去对出口合同 |
| `SUPPLIER` | 供应商往来 | 去对采购付款单（**含退款，进账也算**） |
| `TAX_REFUND` | 出口退税 | 先只记着，功能以后做 |
| `OTHER` | 不用核销 | 二级分类：银行利息、内部划转、保证金退回、其他 |

`OTHER` 那一档不是凑数：银行对账单里天天有利息和手续费，没有这一档，人会被
逼着把它们硬塞进「客户收款」——**那比空着更糟**。二级分类沿用出口现有的
`irrelevant_type`（少掉「供应商退款」，它归 `SUPPLIER`）。

**归属可改**，改错很正常。出口现在的「撤销标记」就是干这个的，保留。

**二、把出口那张表并进来**。要补的列：收款账户、汇款附言（**扫合同号靠它，
不能丢**）、对方账号、来源、归属/二级分类。已有数据按规则迁：原来「与应收
无关」的按二级分类映射到 `OTHER` 或 `SUPPLIER`，其余进账落 `CUSTOMER`。

**三、两个页面变成同一份数据的两个视角**。收款对账只列 `CUSTOMER` 的，
供应商那边只列 `SUPPLIER` 的。核销记录仍归各自的服务，**只存 `bank_txn_id`
这个引用，不抄一份行**——采购的 `supplier_payments` 已经有这个字段了，出口
那边照做。

**四、去掉「只有出账能匹配」那条限制**，否则供应商退款照样对不上。

#### 顺序与风险

迁移要按「先加列、双写、再切读、最后删旧表」四步走，每一步单独上线——
`check-migration-safety.sh` 那条规矩（一次部署内不能既删又读）在这里正好适用。
最危险的一步是第二步的数据迁移：**同一笔银行流水可能已经在两张表里各有一份**
（两张表的流水号去重是各管各的），迁移脚本必须按「流水号 + 金额 + 日期」查重
并把冲突单独列出来给人看，不许自动合并。

#### 第一步已完成（2026-08-26）

迁移 `procurement/00027_bank_transaction_ownership.sql`：加 `ownership` 与
`ownership_detail` 两列，并**按事实回填**——已经被某张付款单认领的流水归
`SUPPLIER`（有付款单指着它，它当然是供应商那条线上的），其余一律留空。
出账十有八九是付供应商的，也没替人填：一个猜出来的归属会让人以为已经有人
看过这一笔了。

**顺带把第四步一起做了**，因为它就是归属要解决的那个问题：匹配供应商付款
的闸从 `direction != "DEBIT"` 改成看归属（`ownership` 为空或 `SUPPLIER`
才放行），并且**匹配这个动作本身会把还空着的归属补成 `SUPPLIER`**——省掉
一次多余点击，也让列表上的「待处理」是准的。

两道新闸：已被付款单认领的流水不许把归属改走（否则那张付款单就指着一笔写着
「我不是供应商的钱」的流水）；二级分类只有「不用核销」那一档能填。

**改掉了一条把 bug 当成规矩的旧断言**：`TestBankStatementLifecycle` 里原本
写着「进账一律不许匹配付款单」。现在拒绝的理由从「它是进账」换成了「它不是
供应商那条线上的」——同一笔进账，归属为空时能匹配，归给客户后就不能。

**验红**：把闸退回只认出账，`TestSupplierRefundIsAnIncomingRowAndMustStillMatch`
当场报「供应商退款对不上号了：BANK_TXN_DIRECTION」——正是那个 bug 的现场。

#### 第二步动手前查到的一件事：外键（2026-08-26）

写迁移之前先去看了出口那张表的周边，发现一处比「搬行」难得多的东西：

    receipt_allocations.transaction_id BIGINT NOT NULL REFERENCES bank_transactions(id)

**核销记录用外键指着行的 id。** 行一旦搬到另一个库，id 会重新生成，这些
外键就全断了。所以第二步真正的工作量不是把行复制过去，是复制完之后让每一条
核销记录重新指对地方——而且中间任何一步失败，账就对不上了。

这也否掉了「一条 INSERT ... SELECT 搞定」那种想法。

**所以第二步先出一份只读报告**（`scripts/f2-bank-merge-report.sh`），回答
三个只有真实数据能回答的问题：两张表各多少行、出口那边挂着多少条核销记录、
同一笔流水是不是已经在两张表里各有一份。**报告不改任何数据**，看完再定做法：

| 报告结果 | 做法 |
|---|---|
| 两边都很小、核销记录 0 条 | 直接并，一次搞定 |
| 核销记录不少，但没有重号 | 分四步走：加列 → 双写 → 切读 → 删旧表；核销记录加一列 `bank_txn_id` 指新 id，老列留着不动，最后再删 |
| 有重号 | **停下来人工核对**。同号不一定同一笔；真是同一笔的话，留哪一份、核销跟谁走，都是判断不是规则 |

本地开发库两张表都是 0 行，所以这份报告要在**生产**上跑才有意义。

**还剩二、三两步**（并表与两个页面变成同一份数据的两个视角）。
