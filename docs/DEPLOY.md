# 上云清单

这份清单存在的理由：**部署那天不会有人重新想一遍这些事。** 到时候执行的是 `docker compose up`，用的是仓库里那份配置——所以每一条「上线前记得改」如果不写下来，就一定会漏。

> 首次上线之后的日常发布走自动化管道（GitHub Actions 构建 → GHCR → SSM 部署），
> 方案见 [DEPLOY-PIPELINE.md](./DEPLOY-PIPELINE.md)。本清单管的是"第一次"和"环境本身"。

---

## 一、只开一个端口

```
443    网页（https）
```

**其余一个都不要开。**

仓库里所有内部端口已经绑在 `127.0.0.1` 上了（11 个服务 + Postgres + Redis + Kafka + MinIO），云上**保持原样即可，不需要再改**。`127.0.0.1` 在云主机上和在笔记本上是同一个意思：只有这台机器自己能连。

三件容易搞错的事：

**① 不要指望防火墙。** Docker 发布端口时会自己往 iptables 里写规则，**位置在 ufw 的规则之前**。你配好 ufw、以为 5432 关着，实际它照常应答。绑定地址是真正起作用的那道控制，防火墙是第二道。

**② 内部服务现在要求签名，但仍然不该暴露。** 2026-08-08 之前它们照单全收网关递来的那句「这位是 X 公司的 Y 员工」——**任何能连上 9001 的人，不用密码就是所有租户的管理员**。现在每个调用都要带 `INTERNAL_SIGNING_KEY` 签出来的签名，门槛变成「够得着端口**并且**知道密钥」。

这是第二道防线，不是替代第一道：所有服务共用一个密钥，所以它证明的是「是我们中的一个」，不是「是邮件服务」。绑定地址仍然是第一道。

**③ 云主机开机就在被扫。** 5432、6379、9000 都在自动扫描器的必扫列表里。这不是有人针对你，是背景噪音，但结果一样。

要从云上连数据库调试时，走 SSH 隧道或者 `docker exec`，不要为此打开端口：

```bash
ssh -L 5433:127.0.0.1:5433 你的服务器     # 之后本机 psql -h 127.0.0.1 -p 5433
```

## 二、网关放在反向代理后面

`8080` 是唯一从外面能连的端口，它应该只对本机开放，由 nginx 占着 443 转进来。

改 `deploy/docker-compose.services.yml` 里 gateway 那段：

```yaml
ports:
  - "127.0.0.1:8080:8080"
```

nginx 那边必须**覆写**而不是追加转发头，否则下面那个开关会被伪造：

```nginx
proxy_set_header X-Forwarded-For $remote_addr;   # 覆写，不是 $proxy_add_x_forwarded_for
proxy_set_header Host $host;
proxy_pass http://127.0.0.1:8080;
```

## 三、必须设的环境变量

放在 `deploy/.env`（不进代码仓库）。

| 变量 | 为什么 |
|---|---|
| `JWT_SECRET` | **最要紧的一条。** 默认值是 `dev-secret-change-in-production`，知道这串字符的人可以伪造任何人的登录态——不需要密码，不经过登录页，所有限速都碰不到他。换成随机值：`openssl rand -base64 48` |
| `COOKIE_SECURE=1` | 登录态现在住在 httpOnly cookie 里（2026-08-15 起，脚本读不到、偷不走）。这个开关给 cookie 打上「只走 HTTPS」的标记——**nginx 的证书配好就必须开**。不开的话，任何一次误走 http:// 的请求都会把会话 cookie 明文送上网线 |
| `TRUST_PROXY_HEADERS=1` | 只有在上面那个 nginx 配置到位之后才开。不开的话，登录限速会把**全世界当成同一个来源**（都来自 nginx），20 次错密码锁住所有人；乱开的话，转发头可以伪造，等于没有限速。**导出记录里的「来源地址」也走这条路**——不开就是每一条都写 `127.0.0.1`，等于没记 |
| `ADMIN_EMAIL` / `COMPANY_MAIL_DOMAINS` | 第一个租户和它的域名 |
| `ADMIN_INITIAL_PASSWORD` | 默认值是 `admin123`，**低于系统要求所有人达到的门槛**。启动日志里会有一行警告 |
| `MAIL_CRED_KEY` | 员工邮箱凭据的加密密钥。**没有它服务起不来**，这是有意的 |
| `INTERNAL_SIGNING_KEY` | 服务之间互相证明「我是自己人」的密钥，**11 个服务必须是同一个值**。没有它服务起不来，也是有意的——一个能从仓库里读到的签名密钥谁也证明不了。`openssl rand -hex 32` |
| `GOOGLE_OAUTH_CLIENT_SECRET` | 用 Google 登录邮箱时需要 |
| `FRONTEND_BASE_URL` | 激活链接里的域名，必须是外面能打开的那个 |
| `MAIL_PUBLIC_BASE_URL` | 发出去的邮件里图片的地址，同上 |

**每一个都要重新生成，不能沿用本地那份。** 在笔记本上出现过的密钥不是生产密钥——它进过文件、可能进过 shell history、可能进过某次截图。

**`COMPANY_MAIL_DOMAINS` 要把 `gmail.com` 去掉。** 它在开发配置里是为了用 Gmail 的 `+别名` 造测试员工。

留着不再有「路由」上的危险——**登录已经不看域名了**（2026-08-09 起，见下）。现在它只管一件事：**哪些地址可以被添加成员工**。留着 `gmail.com` 意味着管理员能把任意一个 Gmail 地址加进公司通讯录并发出激活邀请，仍然该去掉，只是后果比原来小。

### 登录不再靠域名判断公司

原来是「`@` 后面那段 → 哪家公司 → 再查账号」。`tenant_domains.domain` 是主键，一个域名只能属于一家公司——**对自有域名正确，对 gmail.com / qq.com / 163.com 完全错误**：不是「路由到错的公司」，而是第二家用 QQ 邮箱办公的公司**根本注册不进来**，插入会撞主键。

现在邮箱地址全系统唯一，登录直接按地址找账号，账号自己带着公司。域名只保留它本来擅长的那件事：**判断一个地址算不算公司邮箱**（加员工、发邀请时校验，`ListTenantDomains` / `IsTenantDomain`）。

代价写清楚：**同一个邮箱不能在两家公司各有一个账号**。对 ERP 来说这是对的取舍——一个人在两家公司任职，本来就该有两个工作邮箱。


### `.env` 这个方案的上限

环境变量在 `docker inspect` 里是**明文可见**的。所以它的真实保护范围是「能读这个文件的人」≈「能操作这台机器的人」。比写进仓库好得多，但它不是保险箱。

再进一步是云厂商的密钥管理服务（阿里云 KMS、AWS Secrets Manager），启动时去取、不落盘。**不建议第一天就做**：它挡的是「机器已经被人进去了」，而那时候要担心的东西比这把钥匙多。先把上面那些换成随机值，收益大得多。

### 时钟：`INTERNAL_SIGNING_KEY` 的隐藏依赖

服务之间的签名里带时间戳，两边相差超过 **2 分钟**就判失效（`pkg/grpcx/signing.go` 的 `signatureWindow`）。

11 个服务在同一台机器上时共用一个时钟，这条不会出问题；云主机默认装了时间同步，一般也没事。

**但服务哪天拆到多台机器上，这条就成了真依赖。** 时钟不同步的症状是签名成片失败，而且随机、间歇——最难查的那一类。拆机器那天要连着 NTP 一起检查。

### 换这把钥匙目前做不到无缝

共享密钥的固有代价：**11 个服务必须同时换**。现在只能「全停 → 改 `.env` → 全起」，中间有几秒不可用。

要无缝，得让服务在过渡期同时接受新旧两把钥匙（读两个变量，验签时都试一遍，换完再撤掉旧的）。**现在没做。** 值不值得做取决于轮换频率：

- 「泄露了才换」——几秒停机可以接受，不用做
- 「定期轮换」——先补这个，否则每次轮换都是一次计划内停机

同一件事对 `JWT_SECRET` 更严重：换它会把**所有人登出**（这正是 `#68` 存在的理由——单独结束一个人的登录不该动到全公司）。挑不忙的时候换。

## 五、文件存哪：上云换成云厂商的对象存储

**已定：上云后不自己跑 MinIO，改用云厂商的对象存储**（阿里云 OSS / 腾讯云 COS / AWS S3 均可，按机房就近选）。

理由是运维面：自己跑 MinIO 意味着这台机器的硬盘就是唯一一份，扩容、快照、异地备份全要自己做——而里面装的是合同扫描件、客户来信的原始 MIME 和附件，丢一次就没有第二份。

**代码不用改。** 存储从第一天起就走 S3 那套通用接口（见 `pkg/blobstore/blobstore.go` 开头那行注释），MinIO 只是本地的实现。换的时候只动环境变量：

| 变量 | 本地现在 | 云上 |
|---|---|---|
| `MINIO_ENDPOINT` | `minio:9000` | 厂商的内网/公网 endpoint，如 `oss-cn-hangzhou-internal.aliyuncs.com` |
| `MINIO_PUBLIC_ENDPOINT` | `localhost:19000` | 浏览器够得着的那个域名（**必须和上面分开**，签名把 Host 也签进去了） |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | `erp` / `erp_dev_password` | 厂商的 AccessKey，权限**只给这一个桶** |
| `MINIO_BUCKET` | `erp-files` | 建好的桶名 |
| `MINIO_USE_SSL` | 空 | `1` |
| `MINIO_REGION` | 空 | 桶所在区域，如 `cn-hangzhou`（不能靠自动发现，服务在容器里探不到公网 endpoint） |

三个容易踩的点：

**① 桶必须是私有的。** 所有读取都走限时签名 URL，桶本身公开可读就等于把全部合同和来信附件挂到了公网。

**② 内网 endpoint 走内网。** 服务自己读写用内网地址（不计流量费也更快），只有给浏览器的签名 URL 用公网地址。这就是上面两个变量分开的原因。

**③ 生命周期规则要配。** 邮件正文里缓存的远程图片会持续增长（现在 2618 封信约 3 万个图片引用，粗估 1 GB 出头），设个「N 天后转低频/删除」的规则，别让它无限长。

## 五之二、人多起来之后的两个数字

平时不用管，**客户超过几十人就得看一眼**。

### 数据库连接：11 × 8 = 88，上限 100

每个服务的连接池默认 8 条（`pkg/pgdb.DefaultMaxConns`）。11 个服务共用一个
Postgres，`max_connections` 是 100，所以预算是 88，剩下 12 条留给 `psql`
和 `pg_dump`。

**要给某个服务多一点，在它的 `DB_DSN` 后面加 `?pool_max_conns=N`**（代码只在
DSN 没写的时候才填默认值）。但加之前先算总和——超了 100 之后，第 11 个服务
要第 9 条连接的那一刻就是它挂掉，而且报错看着像是数据库出了问题。

真要整体调高，得同时改 Postgres 的 `max_connections`，每条连接大约几 MB。

### 收信周期：300 个邮箱在 8 个并发下，每箱超过 3.2 秒就追不上

一轮的耗时 ≈ 邮箱数 × 每箱耗时 ÷ 并发数，而它必须小于 `MAIL_SYNC_INTERVAL`
（默认 2 分钟）。测量见 `services/mail/internal/app/syncscale_test.go`：

| 邮箱数 | 并发 | 一轮耗时 | 每箱超过多久就追不上 |
|---|---|---|---|
| 20 | 8 | 10s | 48s |
| 80 | 8 | 13s | 12s |
| **300** | **8** | **44s** | **3.2s** |
| 300 | 24 | 19s | 9.6s |

追不上的症状**不是报错**，是每一次 tick 都落在上一轮还没跑完的时候，
「两分钟内看到回信」悄悄变成谁也没量过的一个更长的数。

**先别急着调高 `MAIL_SYNC_CONCURRENCY`。** 这个上限管的不是我们的资源，
是**一个客户端可以同时向一台邮件主机要多少东西**——一家公司 300 个邮箱
多半在同一个服务商上，24 路并发从同一个 IP 打过去，撞限流甚至被封的风险
是真的。真到追不上的那天，按活跃度分级排期（活跃的两分钟，闲置的半小时）
比调高并发好：它既缩短了一轮，又**减少**了对服务商的压力，而不是增加。

## 六、上线前逐条确认

- [ ] `nmap` 扫一遍自己的公网 IP，**除了 443 什么都不该开**
- [ ] `JWT_SECRET` 已换成随机值（会把所有人登出一次，选个不忙的时候）
- [ ] nginx 覆写了 `X-Forwarded-For`，并且 `TRUST_PROXY_HEADERS=1`
- [ ] `COOKIE_SECURE=1`（HTTPS 就绪后；见第三节——没有它，会话 cookie 会跟着任何一次 http:// 请求明文出门）
- [ ] `COMPANY_MAIL_DOMAINS` 里没有公共邮箱域名
- [ ] 管理员密码不是 `admin123`（看启动日志有没有那行警告）
- [ ] 库密码和 MinIO 密钥已经不是仓库里那几个
- [ ] `INTERNAL_SIGNING_KEY` 重新生成过，**11 个服务读到的是同一个值**
      （不一致的症状不是全挂，是某两个服务之间 `Unauthenticated`，看着像网络问题）
- [ ] 机器的时间同步是开着的（服务间签名有 2 分钟窗口）
- [ ] 对象存储换成了云厂商的桶，**桶是私有的**，内网/公网 endpoint 分开配
- [ ] 桶上配了生命周期规则
- [ ] Redis 可达（邮箱门禁和会话吊销都用它；Redis 挂了邮箱不可用，
      会话吊销则停在最后已知状态继续执行，不会把人锁在门外）
- [ ] 数据库有备份，而且**恢复流程真的走过一遍**
- [ ] `make audit-mail` 跑过，**没有 ✗**
      （✗ 是我们代码造成的沉默损坏——不报错、不进日志、只有正好打开那封信的人
      才看得见。2026-08-11/12 找到的三个 bug 里有两个是这样扫出来的，不是等人报障）
- [ ] 客户超过几十人的话，第五之二节那两个数字算过一遍
      （连接池总和 ≤ `max_connections`；收信一轮 < `MAIL_SYNC_INTERVAL`）
