# Excel 导入生成采购单实现方案

## 1. 目标

员工在邮件正文或附件转换出的 Excel 预览窗口中，点击“导入采购单”，经过供应商选择、
采购需求匹配和数据校验后，由系统创建一张采购单草稿。创建成功后系统自动生成全局唯一的
采购单号，并直接打开新采购单详情。

本功能只生成 `DRAFT` 状态的采购单，不自动提交审批，也不代表已经向供应商正式下单。

## 2. 关键业务约束

### 2.1 采购单必须来源于真实采购需求

现有采购模型要求采购单明细引用 `purchase_requirements`。Excel 中的一行产品不能绕过采购
需求直接成为采购单明细，否则客户尚未成交的普通询盘也可能触发真实采购承诺。

因此导入时必须满足以下任一条件：

1. Excel 行携带系统采购需求 ID，并且该需求仍有未下单数量；
2. 系统根据产品、规格、单位和数量找到候选采购需求，由员工手工确认匹配；
3. 找不到采购需求的行不能导入采购单，应继续走“建立询价案件”，或由有权限的员工先建立
   手工例外采购需求。

Excel 导入不得自动创建采购需求，也不得自动把询价案件转成采购单。

### 2.2 一张采购单只能对应一个供应商

导入向导必须先选择一个启用中的供应商。供应商 ID 来源于系统主数据，供应商名称和编码在
创建时保存快照，不能直接相信 Excel 中填写的显示文本。

如果同一个 Excel 中包含多个供应商，应拆成多张采购单，每张单分别确认后创建。

### 2.3 导入后直接进入采购单草稿

创建成功后后端返回：

```json
{
  "id": 123,
  "poNo": "PO-202608-0001",
  "status": "DRAFT"
}
```

前端关闭 Excel 窗口并跳转到：

```text
/purchase-orders?order=123
```

采购单页面读取 `order` 参数并自动打开该采购单详情或编辑窗口。页面同时提供“返回 Excel
来源”的链接，方便员工重新核对原始邮件。

## 3. 采购单号与唯一性

### 3.1 复用现有单号服务

系统已经配置采购单编码规则：

```text
业务类型：PURCHASE_ORDER
前缀：PO
周期：MONTHLY
流水位数：4
示例：PO-202608-0001
```

创建采购单时继续由 procurement 服务调用 masterdata 的：

```go
numbering.Next(ctx, "PURCHASE_ORDER")
```

不允许前端调用 `/numbering/next` 预取单号，也不读取 Excel 中的采购单号作为正式单号。
只有所有导入行、供应商和采购需求校验通过以后，后端才取号并写入采购单。

### 3.2 唯一性的三层保证

1. `number_sequences` 使用原子 `INSERT ... ON CONFLICT DO UPDATE` 递增，同一租户、业务类型、
   月份下的并发请求不会得到相同流水号；
2. `purchase_orders` 已有数据库唯一约束 `UNIQUE (tenant_id, po_no)`；
3. 创建接口收到唯一冲突时不得静默覆盖旧单，应记录错误并安全重试一次取号；仍失败则返回
   明确错误，不创建半张采购单。

系统只保证单号唯一，不追求绝对连续。校验失败时不应取号；服务异常导致少量跳号可以接受，
但绝不能重复或复用已经发出的单号。

## 4. Excel 格式

当前询盘 Excel 的固定列继续保留：

1. 产品
2. 材质/标准
3. 牌号/等级
4. 厚度
5. 宽度
6. 长度/形式
7. 表面要求
8. 涂层/镀层
9. 公差
10. 卷重
11. 卷内径
12. 包装
13. 交期
14. 付款条件
15. 贸易术语
16. 港口
17. 单位
18. 备注
19. 数量
20. 单价
21. 总价

用于采购单导入时，系统还需要以下内部匹配信息：

| 字段 | 必填 | 处理方式 |
|---|---:|---|
| 采购需求 ID | 条件必填 | 系统导出的模板可写入；客户原始 Excel 通常没有，需要人工匹配 |
| 产品/SKU | 是 | 根据内部产品目录确认，不能只保存客户自由文本 |
| 数量 | 是 | 必须大于 0，且不能超过采购需求未下单数量 |
| 单价 | 否 | 空值按 0 保存草稿；必须为非负数 |
| 单位 | 是 | 必须与采购需求单位一致，暂不自动换算 |
| 交期 | 否 | 可作为采购单预计交期的候选值 |

不建议改变面向客户询盘的 21 列格式。内部的采购需求 ID、产品 ID、SKU ID 可以保存在系统
生成的专用采购导入模板中，或仅保存在导入预览会话中，不必暴露在客户看到的表格里。

## 5. UI 设计

### 5.1 Excel 预览窗口

在现有按钮区域增加：

```text
[关闭] [建立询价案件] [导入采购单] [下载 Excel]
```

“导入采购单”显示规则：

- 用户拥有 `procurement:order:write` 时显示；
- Excel 已成功解析且存在明细行时可点击；
- 预览只返回前 200 行而不是完整文件时置灰，并说明“请下载核对或上传完整采购模板”；
- 当前文件没有可识别的数量列时置灰，并直接显示原因；
- 如果来源明显是普通客户询盘，按钮仍可进入匹配向导，但不能跳过采购需求确认。

### 5.2 导入向导

点击按钮后打开三步向导。

#### 第一步：采购单基本信息

- 供应商：必填，从启用中的供应商主数据选择；
- 币种：默认使用供应商币种，可修改；
- 预计交期：从 Excel 交期提取，可修改；
- 备注：自动写入来源邮件主题、邮件 ID、附件 ID 或文件名；
- 采购单号：显示“保存后由系统生成”，不提供输入框。

#### 第二步：明细匹配

逐行展示：

| Excel 产品/规格 | Excel 数量 | Excel 单价 | 匹配采购需求 | 可下单数量 | 结果 |
|---|---:|---:|---|---:|---|
| 镀锌卷 G60 0.8×1500 | 1600 |  | CT-xxx 第 2 行 | 1600 | 已确认 |

匹配状态：

- `MATCHED`：唯一候选，仍需员工确认；
- `MULTIPLE`：多个候选，必须手工选择；
- `NOT_FOUND`：没有采购需求，不能提交；
- `QTY_EXCEEDED`：数量超过剩余需求，必须修改或拆分；
- `UNIT_MISMATCH`：单位不一致，不能自动换算；
- `DUPLICATED`：同一采购需求在本次导入中重复出现，应合并或删除一行。

#### 第三步：创建确认

展示供应商、币种、明细数量、总吨数和总金额。员工确认后才调用创建接口。创建成功显示：

```text
采购单 PO-202608-0001 已建立为草稿
```

随后自动进入该采购单。

## 6. 后端接口

建议使用“预览”和“确认”两个接口，禁止上传后未经确认直接写正式业务表。

### 6.1 导入预览

```text
POST /api/purchase-orders/imports/preview
权限：procurement:order:write
```

请求可以引用邮件 Excel 转换结果，也可以上传 `.xlsx`：

```json
{
  "sourceMailId": 2020,
  "sourceAttachmentId": 88,
  "convertedFileKey": "...",
  "supplierId": 12
}
```

响应返回临时 `importToken`、解析行、候选采购需求和错误信息。预览阶段不生成采购单号，也不
修改采购需求。

### 6.2 确认创建

```text
POST /api/purchase-orders/imports/{importToken}/confirm
权限：procurement:order:write
```

```json
{
  "supplierId": 12,
  "currency": "USD",
  "expectedDate": "2026-09-01",
  "remark": "来源邮件 #2020",
  "lines": [
    { "rowNo": 2, "requirementId": 301, "qty": "1600", "unitPrice": "520" }
  ]
}
```

后端必须再次读取并锁定采购需求，重新验证剩余数量，不能信任预览时的旧结果。确认接口最终
复用现有 `CreateOrder` 用例，而不是另写一套采购单创建规则。

## 7. 幂等与重复导入

网络超时或员工双击不能生成两张采购单。建议新增导入记录：

```text
purchase_order_imports
  tenant_id
  import_token
  source_type: MAIL_EXCEL / UPLOAD
  source_mail_id
  source_attachment_id
  file_sha256
  status: PREVIEWED / CREATED / EXPIRED
  purchase_order_id
  created_by
  created_at / expires_at
  UNIQUE (tenant_id, import_token)
```

确认接口在事务中锁定导入记录：

- 第一次确认创建采购单并写入 `purchase_order_id`；
- 相同 token 再次确认直接返回已经创建的采购单；
- 相同文件哈希再次导入时提示“这个文件曾生成采购单 PO-xxx”，由员工决定是打开旧单还是
  创建新的导入会话；
- 不能仅以文件哈希绝对禁止重复，因为同一个模板经过业务确认后可能确实需要再次采购。

## 8. 安全与数据校验

- 只接受 `.xlsx`，限制文件大小、工作表数量和总行数；
- Excel 公式按计算结果读取，不执行宏、外部链接或嵌入对象；
- 文本以普通字符串处理，防止公式注入；
- 金额、数量使用 decimal 字符串，禁止 `float64`；
- 供应商、采购需求、邮件和附件都必须校验租户；
- 邮件来源还要校验当前员工是否有权读取该邮件；
- 创建前重新验证采购需求状态和未下单数量；
- Excel 中的产品名、供应商名、采购单号都不能作为可信主键；
- 创建动作写审计日志，保存来源邮件、附件、文件哈希、操作者和解析结果版本。

## 9. 错误处理

| 错误码 | 提示 |
|---|---|
| `PO_IMPORT_FORMAT_INVALID` | Excel 格式无法识别 |
| `PO_IMPORT_TOO_LARGE` | 文件行数或大小超过限制 |
| `PO_IMPORT_REQUIREMENT_REQUIRED` | 有明细尚未匹配采购需求 |
| `PO_IMPORT_QTY_EXCEEDED` | 导入数量超过采购需求未下单数量 |
| `PO_IMPORT_UNIT_MISMATCH` | Excel 单位与采购需求不一致 |
| `PO_IMPORT_ALREADY_CREATED` | 本次导入已经生成采购单 |
| `PO_IMPORT_EXPIRED` | 导入预览已过期，请重新导入 |
| `PO_NUMBER_CONFLICT` | 采购单号生成冲突，请重试 |

任何一行失败时整张采购单不落库，不允许只创建部分成功的采购单。

## 10. 分阶段实施

### P1：当前 Excel 预览增加入口

- 增加“导入采购单”按钮；
- 基本信息和明细匹配向导；
- 复用当前 21 列解析结果；
- 只允许匹配现有采购需求；
- 创建草稿并跳转采购单详情。

### P2：采购单专用 Excel 模板

- 在待采购页面勾选需求并导出内部模板；
- 模板携带采购需求 ID 和内部产品标识；
- 支持员工填写供应商报价后重新导入；
- 减少产品和需求的人工匹配。

### P3：审计与大文件异步处理

- 持久化导入会话和重复导入提示；
- 大文件通过异步任务解析并使用 SSE 通知；
- 增加导入历史、失败报告 Excel 和管理员审计页面。

## 11. 必测场景

1. 100 个并发创建请求得到 100 个不同采购单号；
2. 同一 `importToken` 重复确认只生成一张采购单；
3. 两人同时导入同一采购需求时，后确认者因剩余数量变化失败；
4. 数量超额、负数单价、重复需求、单位不一致均不创建采购单；
5. 跨租户供应商、需求、邮件或附件均返回无权访问；
6. 普通客户询盘没有采购需求时不能直接生成采购单；
7. 创建失败不留下采购单头、孤立明细或半完成导入记录；
8. 创建成功后自动打开正确采购单，单号、金额和 Excel 明细一致；
9. 导入只创建草稿，不自动提交审批；
10. 中英文和西班牙文按钮、错误提示和向导字段完整。

## 12. 本阶段明确不做

- 不修改现有采购单创建和审批代码；
- 不允许 Excel 指定正式采购单号；
- 不从普通客户询盘自动建立真实采购需求；
- 不自动提交审批或发送供应商邮件；
- 不因为 Excel 导入而改变码头到货、出运或库存台账逻辑。

## 13. 完整后续路线图

Excel 导入不是一个孤立按钮。最终业务链路应当是：

```text
客户邮件 / 工厂报价 Excel
  → Excel 解析与预览
  → 询价案件或采购需求匹配
  → 导入采购单草稿
  → 采购单审批
  → 向供应商正式发单
  → 工厂生产进度跟踪
  → 工厂送达码头库
  → 码头到货确认
  → 衔接出运
  → 供应商付款与采购分析
```

以下阶段应当按顺序实施，前一阶段验收通过后再进入后一阶段。

`procurement:receipt:write`，使物流人员能登记到货但不能修改供应商订单。

验收标准：

- 每个按钮和 API 都执行相同的后端权限检查；
- 物流角色不能创建、改价或提交采购单；
- 采购专员不能自行审批自己提交的订单；
- 财务不能修改采购数量和供应商；
- 超级管理员继续拥有所有权限。

## 14. 建议的实际开发顺序

为了降低一次改动过大导致回归的风险，建议按以下批次提交：

1. **批次 1：UI 入口整合**
   采购管理工作台和二级导航，不改变权限和后端业务。
2. **批次 2：导入预览**
   Excel 按钮、导入向导和只读匹配接口，不创建采购单。
3. **批次 3：确认创建**
   导入会话、幂等确认、复用 `CreateOrder`、唯一单号和自动跳转。
4. **批次 4：权限拆分**
   采购角色、订单提交/取消、码头到货独立权限。
5. **批次 5：询价数据范围**
   案件负责人范围和工厂价格字段隔离。
6. **批次 6：采购模板**
   从待采购导出内部模板并重新导入。
7. **批次 7：审批与发单**
   审批通过后生成供应商文件并发送。
8. **批次 8：生产与码头**
   生产进度、分批到货、异常和出运衔接。
9. **批次 9：付款与报表**
   应付、付款、供应商绩效和管理分析。

每个批次都应独立完成迁移、后端权限、接口测试、前端测试、三种语言和 Docker 本地验证，
不得把“页面已出现”作为业务功能已经完成的标准。
